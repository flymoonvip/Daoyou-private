## 第一部分 · 寿元体系

> 原文档版本：v8（2026-11-09）
> 原变更记录：v2 补充人界纪年与自然衰老；v3 补充历练/闭关按年对照与统一时钟方案；v5 新增战败折寿；v6 删除战斗死亡与保命符；v7 与当前代码对齐并覆盖到渡劫；v8 突破改为境界基础寿命。v4 的寿元减半口径已在 v7 撤销。

## 1. 项目背景

当前寿元系统存在三套并行语义：

- **自然衰老**：人界纪年按服务端运行时间推进（现实 12 小时运行时长 = 游戏 1 年），生产环境 cron 持续增加活跃角色 `age`；
- **闭关**：玩家主动推进 `age`，一次 1～200 年；
- **副本选项**：直接扣 `lifespan`（寿元上限）。

三者最终都以 `age >= lifespan` 判定死亡，但玩家只看到一个 `age / lifespan` 比值，无法判断某次操作消耗的是"已活岁月"还是"剩余寿命"，也无法得知即使不操作角色也会随现实时间老去。

同时，各境界纯闭关修为覆盖率仅 10%～19%，寿元实际上没有参与成长决策，只是死亡倒计时。大境界突破把寿元抬到境界基础寿命（炼气 100 → 渡劫 8000），与经验需求 1.7～5.3 倍的增长节奏缺少共同推导依据。

本项目的目标不是简单调高或调低寿元，而是先统一语义，再决定寿元在玩法中的定位。

### 2.3 寿元来源

**初始生成**

- 年龄：`14 + random(0～5)`，即 14～19 岁。
- 寿元：`80 + random(0～19)`；资质分 > 80 再 +20。
- 结果区间：80～99；高资质 100～119。

代码：`packages/game-rules/src/character/creation/CharacterGenerator.ts`；转世建号 `externalJourney.ts` 使用同一寿元口径，年龄为 14～17 岁。

**大境界突破：切换境界基础寿命**

只有跨大境界才改变寿元，阶段内突破不影响。突破时不再把固定值累加到当前寿元，而是把寿元抬到目标境界的基础寿命：

`lifespan = max(当前 lifespan, 目标境界基础寿命)`

这样延寿丹、灵果、宗门恩赏带来的额外寿元不会被覆盖，也不会因反复突破重复叠加基础值。

| 境界 | 境界基础寿命 | 相对上一境界净增 |
| --- | --- | --- |
| 炼气 | 100（初始个体 80～119） | — |
| 筑基 | 200 | +100 |
| 金丹 | 500 | +300 |
| 元婴 | 1200 | +700 |
| 化神 | 2000 | +800 |
| 炼虚 | 3000 | +1000 |
| 合体 | 4000 | +1000 |
| 大乘 | 5000 | +1000 |
| 渡劫 | 8000 | +3000 |

代码：`packages/game-rules/src/cultivation/breakthroughCalculator.ts`（`LIFESPAN_BONUS_BY_REALM`，数值按基础寿命解释）、`CultivationEngine.ts`。当前 `CultivationEngine` 仍使用 `cultivator.lifespan += lifespanGained` 的相加写法，落地本口径时需改为上式。

**耐药与单世上限（v10 已定）**

- 同一种丹药在同一世内重复服用，第 n 次效果为 `基础值 × 0.85^(n-1)`，最低保留 20%；按丹药 ID 分别计数。
- 单世丹药/灵果累计增加的寿元设上限，建议为当前境界基础寿命的 100%（例如炼气最多 +100 年、渡劫最多 +8000 年），具体数值待数值校准。
- 突破切换境界基础寿命不占用该上限；延寿丹只抬高 `lifespan`，不推进 `age`。
- 目的：避免高境界靠无限嗑药把寿元推到失控，同时保留低境界延寿丹的体感。

### 2.5 人界纪年法与自然衰老

人界纪年不是展示用的日期，而是寿元系统的被动时钟。下表为 **v15 目标口径**；首行是尚未替换的现状，落地前不能假设 `world_clock` 已存在。

| 项目 | 规则 | 代码 |
| --- | --- | --- |
| 现状（v15 前） | 固定纪元 2026-10-18 00:00（UTC+8）+ 墙钟时间，停机期间仍照常衰老 | `GAME_CALENDAR_EPOCH_MS`、`advanceNaturalAging` |
| 纪年起点 | 服务端首次建立世界时钟时登记「人界元年」，不再绑定北京时间 | 新增 `world_clock` 表；`GAME_CALENDAR_EPOCH_MS` 退役 |
| 单次运行起点 | 服务端进程启动时刻（机器时间），本次运行只累计启动后的时长 | `process.uptime()` / 单调时钟 |
| 停机 | 维护、重启、宕机期间时钟暂停，不推进年龄与历练 | `world_clock.accumulated_ms` |
| 现实→游戏月 | 现实 60 分钟 = 游戏 1 月 | `REAL_MS_PER_GAME_MONTH` |
| 现实→游戏年 | 现实 12 小时运行时长 = 游戏 1 年 | `REAL_MS_PER_GAME_YEAR` |
| 历法结构 | 30 日/月、12 月/年 | `calendar.ts` |
| 自然衰老 | 每满 1 游戏年，`age += 1`，锚点前移并保留不足一年的零头 | `advanceNaturalAging` |
| 调度 | 生产环境每 10 分钟扫描一次；只处理 `aging_synced_at` 早于「世界时钟 − 1 游戏年」的 active 角色 | `BACKGROUND_SCHEDULES`、`runWorldAgingTickJob` |
| 死亡 | 结算后 `age >= lifespan` 直接 `status = 'dead'`、写 `died_at`，不生成寿元故事 | `internalCron.ts` |
| 展示 | 顶部 HUD 显示「人界X年X月X日」 | `useGameHudModel`、`GameTopHud` |

**为什么改时钟（v15）**：原实现用固定 UTC+8 纪元 + 墙钟时间，服务端维护、停机或宕机期间角色仍在衰老，玩家会因运维损失寿元与历练收益。改为「运行时钟」：

- `world_clock` 单行持久化 `accumulated_ms`；进程启动时读取，运行期间用单调时钟累加，每 5 分钟落盘一次，优雅停机时再落盘。
- 世界时间 `worldNow = accumulated_ms + (monotonicNow - startedAt)`；停机期间不累加，所以维护不消耗寿元。
- 崩溃最多丢失一个落盘周期（约 5 分钟），远小于 1 游戏年，不会造成可见损失。
- 一次性迁移把「旧纪元到切换时刻」的差值写入 `accumulated_ms`，保证 HUD 纪年不断档。
- 多实例部署时只允许 runtime leader 推进与落盘，其余实例读取同一快照。

因此寿元同时具有两种时间尺度：

- **游戏内尺度**：100/200/500/1200/2000/3000/4000/5000/8000 年，用于闭关与修为预算；
- **运行尺度**：1 游戏年 = 12 小时**服务端运行时长**，寿元是账号级运行倒计时，停机不流逝。

> 下表的"天"均按服务端 24 小时持续运行折算，仅用于内部测算，不作为玩家界面展示（v10/v15 已定）。

| 境界 | 剩余寿元（初始 14～19 岁） | 运行可存活天数 | 约合 |
| --- | --- | --- | --- |
| 炼气 | 61～105 年 | 30.5～52.5 天 | 约 1.0～1.8 个月 |
| 筑基 | 181～186 年 | 90.5～93 天 | 约 3.0～3.1 个月 |
| 金丹 | 481～486 年 | 240.5～243 天 | 约 8.0～8.1 个月 |
| 元婴 | 1181～1186 年 | 590.5～593 天 | 约 1.6 年 |
| 化神 | 1981～1986 年 | 990.5～993 天 | 约 2.7 年 |
| 炼虚 | 2981～2986 年 | 1490.5～1493 天 | 约 4.1 年 |
| 合体 | 3981～3986 年 | 1990.5～1993 天 | 约 5.5 年 |
| 大乘 | 4981～4986 年 | 2490.5～2493 天 | 约 6.8 年 |
| 渡劫 | 7981～7986 年 | 3990.5～3993 天 | 约 10.9 年 |

含义：炼气角色即使完全不操作，累计运行约 41 天后也会自然老死；闭关本质上是把这段等待时间"提前烧掉"，换成修为。自然衰老与闭关使用同一个 `age`，因此二者会叠加消耗同一条寿命。

## 3. 寿元消耗途径

### 3.1 自然衰老：运行时间推进年龄

- 入口：`runWorldAgingTickJob`（`apps/api/src/runtime/jobs/internalCron.ts`）
- 规则：`advanceNaturalAging`（`packages/game-rules/src/world/aging.ts`）；每满 1 游戏年 `age += 1`，锚点向前移动一年并保留不足一年的零头
- 时钟：现状为固定纪元 + 墙钟；v15 目标改为 `world_clock` 运行时钟（待实现），现实 12 小时**运行时长** = 1 游戏年，停机暂停
- 调度：生产环境每 10 分钟扫描一次（`*/10 * * * *`），只处理 `aging_synced_at` 落后超过 1 游戏年的 active 角色
- 死亡：`age >= lifespan` 时直接 `status = 'dead'` 并写 `died_at`，不走 `handleLifespan`、不生成寿元耗尽故事
- 环境差异：`CronService` 只在 `NODE_ENV === 'production'` 启动；本地/dev 只能手动调用 `/internal/cron/world-aging-tick`

作用：不依赖玩家操作、持续消耗同一条寿命的被动时钟。它把寿元从"修炼预算"变成了"账号存活时间"，也是炼气角色累计运行约 41 天后自然老死的直接原因。

### 3.2 闭关：推进年龄

- 入口：`apps/api/src/cultivator/application/RetreatApplicationService.ts`
- 规则：`packages/game-rules/src/cultivation/CultivationEngine.ts`，`performCultivation` 中 `age += years`
- 年限：单次 1～200 年；v10 起按境界封顶，见 7.7
- 前置校验：`lifespan - age >= years`，否则拒绝；v10 起还要求闭关后保留最低余寿，见 7.7
- 灵气成本：`ceil(years / 10) × 4`；灵气上限 240，自然恢复 1 点/6 分钟
- 死亡：`age >= lifespan` 时置 `dead`，生成寿元耗尽故事
- 突破：v11 起固定耗时 1 年，`attemptBreakthrough` 使 `age += 1`、历史记录 `years_spent: 1`；突破成功与失败都消耗这 1 年，但失败不折寿

作用：玩家主动推进年龄的路径，可与自然衰老叠加；同时是修为来源之一。v10 起年收益按 7.6 上调到历练的 80%，但仍不产灵石、道具与掉落。

### 3.3 副本选项：削减寿元上限

- 入口：`apps/api/src/dungeon/application/flow/DungeonFlowService.ts`
- 选项成本由 LLM 生成，`costs` 可包含 `lifespan`
- 服务端硬上限：`DUNGEON_LIFESPAN_COST_MAX = 120`
- 公式：`境界基础值 × 难度倍率 × 档位倍率`，最小 1

| 境界 | 境界基础寿命 | 基础值 | 单次成本区间 | 五轮全高成本 | 占基础寿命 |
| --- | --- | --- | --- | --- | --- |
| 炼气 | 100 | 1 | 1～3 | ≈15 | ≈15.0% |
| 筑基 | 200 | 2 | 1～6 | ≈30 | ≈15.0% |
| 金丹 | 500 | 3 | 1～9 | ≈45 | ≈9.0% |
| 元婴 | 1200 | 5 | 2～16 | ≈80 | ≈6.7% |
| 化神 | 2000 | 8 | 3～25 | ≈125 | ≈6.3% |
| 炼虚 | 3000 | 12 | 5～38 | ≈190 | ≈6.3% |
| 合体 | 4000 | 18 | 7～57 | ≈285 | ≈7.1% |
| 大乘 | 5000 | 25 | 9～79 | ≈395 | ≈7.9% |
| 渡劫 | 8000 | 35 | 13～110 | ≈550 | ≈6.9% |

> 单次成本区间 = 基础值 × 难度倍率（0.75～1.8）× 档位倍率（0.5～1.75），并受 `DUNGEON_LIFESPAN_COST_MAX = 120` 截断；占基础寿命按 2.4 的 100/200/500/1200/2000/3000/4000/5000/8000 计算。

执行链：`applyDungeonCosts` → `ResourceEngine` → `updateLifespan(-value)`；若 `age >= lifespan` 且角色仍 active，直接置 `dead`。

作用：唯一直接削减寿元上限的常规玩法；境界越高，相对损失反而越小。

### 3.4 战斗不判死：败方只折寿

现状代码的战斗结算不涉及死亡与寿元：气血归零只结束战斗，不写 `dead`，仓库中也不存在 `resolveBattleDeath` / `death_save`。v6 目标是把战败转换为 3.7 的折寿，仍然不判死。

| 结局 | 概率（同阶） | 折寿倍率 |
| --- | --- | --- |
| 重伤撤退 | 67% | ×1 |
| 濒死 | 33% | ×2 |

- 每差 1 个境界阶位：濒死概率 +10%，上限 100%；不再计算死亡概率。
- 战斗终局直接结算只写状态与 `lifespan`，不写 `dead`；折寿触底时交由寿元扣除路径判死。不需要保留或新增保命符。
- 角色死亡只来自寿元耗尽（自然衰老、闭关、副本折寿、战败折寿触底），以及主动兵解/转世；战斗本身不会直接判死。

作用：战斗从"平行死亡线"降级为寿元消耗渠道，死亡入口收敛为唯一一条。

### 3.5 主动兵解与转世

- `reincarnateActiveCultivator`：主动结束当前角色，`status = 'dead'`
- 死亡后新建角色走初始生成流程，不继承寿元、修为或加成
- `getLastDeadCultivatorSummary` 只提供前世摘要
- 前世加成不在道友侧实现：当前依赖主站，主站尚无建设；道友侧只在外部建号参数中预留 `generation` 等字段，不自行计算加成

### 3.6 灵兽寿元（对照体系）

- 固定上限 1000
- 战死扣 50
- 出战最低寿元 50
- 休养每灵石恢复 10

v10 已定统一命名与规则：对外统一使用「寿元」，人物与灵兽共用 `remaining = lifespan - age` 的展示口径。统一的是命名与剩余量语义，不强行统一恢复方式——灵兽寿元可恢复、固定上限、按次扣减；人物寿元只能靠突破/丹药增长，按年消耗。

### 3.7 战败折寿（v5 新增核心机制）

**定位**：战败不直接判死，而是直接削减这一世的寿元上限。每一次战败都变成不可逆的时间损失，把战斗结果接入同一本寿元账，是方案 B/D「寿元即时间货币」的核心支撑。若折寿本身把寿元打到零，则按寿元耗尽结算死亡（见下方「折寿触底」）。

**规则**

- 触发：战斗终局判负（气血归零）的败方；胜负与折寿值全部由服务端计算，客户端不能上报。
- 折寿对象：败方的 `lifespan` 上限，不扣 `age`；`remaining = lifespan - age` 同步减少。
- 计算公式：`折寿 = 境界基准值 × 结果倍率 × 战斗类型倍率`。

| 境界 | 境界基础寿命 | 基准折寿 | 占基础寿命 | 折合运行时长 |
| --- | --- | --- | --- | --- |
| 炼气 | 100 | 4 | 4.0% | 2 天 |
| 筑基 | 200 | 7 | 3.5% | 3.5 天 |
| 金丹 | 500 | 18 | 3.6% | 9 天 |
| 元婴 | 1200 | 42 | 3.5% | 21 天 |
| 化神 | 2000 | 70 | 3.5% | 35 天 |
| 炼虚 | 3000 | 105 | 3.5% | 52.5 天 |
| 合体 | 4000 | 140 | 3.5% | 70 天 |
| 大乘 | 5000 | 175 | 3.5% | 87.5 天 |
| 渡劫 | 8000 | 280 | 3.5% | 140 天 |

| 结局 | 结果倍率 | 炼气 / 筑基 / 金丹 / 元婴 / 化神 / 炼虚 / 合体 / 大乘 / 渡劫 |
| --- | --- | --- |
| 重伤撤退 | ×1.0 | 4 / 7 / 18 / 42 / 70 / 105 / 140 / 175 / 280 |
| 濒死 | ×2.0 | 8 / 14 / 36 / 84 / 140 / 210 / 280 / 350 / 560 |

| 战斗类型 | 类型倍率 |
| --- | --- |
| 切磋 / 友谊赛（全境界） | ×0（不折寿，受保护） |
| PVE 常规 | ×1.0 |
| 副本首领 / 秘境 | ×1.5 |
| PVP 常规（演武场等） | ×0.5 |
| 野外 PVP / 生死决斗 | ×1.0（不享受保护） |

- v10 已定：**全部 PVE 战败折寿**（常规、副本、秘境、活动），切磋/友谊赛保持 ×0。
- v11 已定：**PVP 折寿保护范围**——切磋/友谊赛在全部境界 ×0；野外 PVP 与生死决斗不享受保护，按对应类型倍率正常折寿。保护规则配置化，不默认提供关闭入口。
- 战斗本身不判死：战斗结算不写 `dead`，`death_save` 保命符下线；气血归零只决定重伤/濒死与折寿档位。
- 折寿触底：若折寿后 `lifespan <= age`，交由统一寿元扣除结算器判死。死亡大类仍为「寿元耗尽（自然死亡）」，来源标记 `battle_defeat`，结算文案为「战败折寿，寿元耗尽」；不再进入「寿元将尽」缓冲，也不保留 `age + 1` 下限。
- 不可自然恢复：折掉的寿元只能靠大境界突破、延寿丹/灵果、宗门恩赏补回。
- 防滥用：
  - 单次折寿硬上限 200 年；
  - 单日累计不超过当前 `lifespan` 的 10%；
  - 同一角色当日第 4 次及以后战败，折寿减半；
  - 同一对手在短期内重复击败，第 2 次起折寿减半（切磋不折寿，不适用）；
  - 组队/宗门战按个人败方结算，不连坐队友。
- 幂等：以 `battleId + 败方 cultivatorId` 为唯一键，战局重放或消息重投不重复扣。
- 与副本折寿叠加：副本内战败可同时触发副本选项折寿与战败折寿，但当日累计仍受 10% 上限约束，结算页分项展示。

**实现落点**

| 层 | 位置 | 改动 |
| --- | --- | --- |
| 规则 | `packages/game-rules/src/combat/` | 新增 `calculateDefeatLifespanLoss` 纯函数（基准表 + 倍率 + 日上限 + 触底判死标记） |
| 内容 | `packages/game-content/src/combat/` | 战败折寿基准值与倍率配置 |
| 服务 | `apps/api/src/combat/application/` 战斗终局结算 | 败方写入 `lifespan`、幂等、写来源日志，统一走死亡结算器 |
| 数据 | `cultivators.lifespan` | 复用，无新列；折寿记录进日志/事件，来源 `battle_defeat` |
| 前端 | 战斗结算页 | 显示「战败折寿 X 年 / 剩余 Y 年」 |

**验收**

- 纯规则单测：基准值、结果/类型倍率、单日 10% 上限、幂等键、触底判死标记。
- 实机：同阶战斗战败一次，结算页与角色面板的 `lifespan` 同步减少；气血归零后角色仍存活；折寿触底时由寿元扣除判定为自然死亡中的特殊战斗死亡，并生成死亡故事/通知；同一 `battleId` 重投不重复扣。

**与现状的关系**：现状战斗不判死也不折寿；v11 目标为「全部 PVE 战败按 3.7 折寿，切磋全境界保护，野外 PVP 与生死决斗不保护」；只有折寿把寿元打到零时，才由寿元耗尽路径判死，战斗本身仍不直接判死。

### 4.2 历练与闭关的按年收益对照（v3 新增）

自然衰老、历练、闭关使用三个不同尺度，必须折算到同一"游戏年"才能比较。

口径：

- 1 游戏年 = 现实 12 小时运行时长；自然衰老每天运行消耗 2 游戏年。
- 历练：`日预算 × 0.008 × 小时 × 0.8~1.2`，单次上限 24 小时（= 2 游戏年）；v14 起改为后台按年自动结算，不再有领取上限。
- 闭关：`日预算 × 0.005 × 年限`，再乘灵根、年限系数、随机、顿悟、瓶颈。

括号内为历练总修为占本境界总经验需求的比例。两种口径的含义：

- 历练：`19.2%/天 × 剩余天数 = 9.6% × 剩余年数 × 日预算`，只受寿元总长限制，余生足以把每个境界刷穿 2.2～4.2 遍。
- 闭关：`0.58%/年 × 剩余年数 × R/(R+2)`（R 为每天闭关年数），上限趋近 `0.58% × 剩余年数`，只有历练总收入的 1/16.7。

**等价换算**

| 等价关系 | 数值 |
| --- | --- |
| 1 天历练 | ≈ 33.3 年闭关 |
| 1 次 200 年闭关（炼气） | ≈ 1,152 修为 ≈ 6 天历练，同时消耗 100 天寿命 |
| 炼气全部 82 年寿元一次性闭关 | ≈ 476 修为 ≈ 2.5 天历练 |
| 自然衰老每天 | 扣 2 年 ≈ 1.16% 日预算的闭关潜力 |
| 同一天历练 | 产出 19.2% 日预算 |
| 瓶颈期（>70%） | 闭关收益减半，倍差扩大到 33:1 |
| 感悟获取 | 历练 18/年 vs 闭关 0.07/年（约 257:1） |

**结论**

1. 历练按运行时间产出、不耗寿元；自然衰老按运行时间扣年、不产修为。二者同频，年龄只决定"能领多少次历练"，不决定单次收益。
2. 闭关是"用未来换现在"：每闭关 1 年，少活 0.5 天，损失约 9.6% 日预算的历练收入，只换回 0.58% 日预算。除寿元本会溢出、需要短期爆发外，闭关是负期望。
3. 突破不耗时、副本只折上限、灵兽寿元可恢复，都会进一步削弱"年"作为成本的地位。
4. 感悟的瓶颈在历练而非寿元：完美突破需 50 感悟，闭关约需 714 年，历练约 2.8 年（现实 1.4 天）。
5. 与第 5 节 P1-11 一致：寿元没有参与成长决策。若要让它参与，必须先统一时间口径（见方案 D）。

> 以上是**未调参的现状基线**。v10 已定把闭关年收益提高到同期历练的 80%（7.6），落地后第 2 条的「16.7 倍差距」与「闭关必然负期望」不再成立；本节的原始测算保留作为对照。

## 5. 问题清单

### P0 · 规则与语义

1. **三套消耗语义**：自然衰老推 `age`、闭关推 `age`、副本扣 `lifespan`，三条路径都能触发 `dead`，但 UI 只有一个比值，玩家无法区分"自然老去/闭关预支/折寿"。
2. **自然衰老死亡静默**：`runWorldAgingTickJob` 直接置 `dead`，未调用 `handleLifespan`，未见寿元耗尽故事与死亡事件投递，只做 `invalidateActiveCultivatorRef` 缓存失效。玩家可能在上线时才发现角色已老死。
3. **突破不耗时**：规则层突破不增加年龄，历史记录 `years_spent: 0`；服务层剧情文案却传 `yearsSpent: 1`。叙事与规则不一致；v11 已定规则层改为固定消耗 1 年（见 9.1）。
4. **函数语义不一致**：`consumeLifespanAndHandleDepletion` 名为"消耗寿元"，闭关调用时传入 `ageAfterConsumption`，实际只做死亡判定，不写寿元。
5. **闭关校验使用陈旧年龄**：校验 `lifespan - age >= years` 读取的是数据库快照，不做按锚点的即时推导；cron 结算前存在约 10 分钟的跨年窗口，可能出现"校验通过、随即被 cron 判死"。
6. **自然衰老不可本地复现**：`CronService.start()` 只在 `NODE_ENV === 'production'` 启动，dev/local 只能手动调用内部接口，测试与联调容易漏掉该时钟。

### P0 · 时间口径（v3 新增）

7. **时间单位三套并存**：历练用现实小时（上限 24h）、闭关用游戏年、副本用轮次、突破不耗时；同一界面同时出现"小时/年/轮"，玩家无法建立统一时间感。
8. **两个现实时间锚点**：`aging_synced_at` 与 `last_yield_at` 各自从现实时间推导，语义重叠但不共享；衰老、历练、挂机对"过去了多久"的答案互相对不上。
9. **闭关跳年与世界纪年永久错位**：闭关 200 年后角色年龄 +200，而 HUD 纪年只按现实推进；角色经历的时间与世界时间永久分离，且没有任何字段记录这段偏移。

### P1 · 数值

10. **现实时间未进入数值设计**：所有寿元/经验/丹药仍按游戏年设计，但实际时钟是现实 12 小时运行时长 = 1 年，没有任何设计文档或公式显式处理"运行时间成本"；v15 改为运行时钟后，停机不再计时。
11. **寿元不参与成长决策**：各境界纯闭关覆盖率仅 10%～19%，渡劫最高也不到 20%，寿元仍不是"能否修上去"的约束。
12. **曲线不匹配**：经验需求在金丹后按约 1.7～2.7 倍增长（炼气→筑基约 4 倍），寿元按境界基础寿命 100/200/500/1200/2000/3000/4000/5000/8000 抬升，没有共同推导依据。
13. **丹药量级脱节**：凡品延寿 +10 年（现实 5 天），渡劫基础寿命 8000 年（现实 4000 天）；延寿丹只在低境界有体感。
14. **经验表与目标天数已对齐**：金丹阶段经验表合计 67,000，目标天数口径 `21 × 3,200 = 67,200`，偏差约 0.3%；其余境界偏差均在 1% 以内。
15. **安全上限形同虚设**：单次寿元变动上限 100,000、绝对值上限 10,000,000，正常玩法几乎触碰不到。

### P1 · 系统一致性

16. **死亡入口体验不一致**：自然老死（cron，静默）、闭关寿尽（`handleLifespan`，有故事）、副本寿尽（`ResourceEngine` 直接 `dead`）。v10 已定统一死亡故事、邮件/站内通知与前世记录；战败折寿触底也走同一结算器。
17. **灵兽寿元规则不同**：灵兽可恢复、固定上限、按次扣减；人物不可恢复、按年消耗。v10 已定统一「寿元」命名与剩余量展示，但保留各自恢复规则。
18. **境界与内容已对齐**：`REALM_VALUES`、增寿表、副本寿元成本、经验表与破境演出均覆盖炼气～渡劫；v10 已定本轮直接开放到渡劫，不做入口封顶。

## 6. 重构方案对比

### 方案 A：寿元货币化（大改）

把"剩余寿元"变成通用资源，所有耗时行为（闭关、副本、探索、赶路、炼丹、突破准备）按年计价；寿元可交易、可抵押，死亡后进入轮回结算。

- 优点：寿元真正进入玩法决策，时间成为核心经济。
- 缺点：改动面最大，涉及所有玩法入口、经济系统、LLM 副本提示词、UI 与存档口径。
- 适用：愿意围绕"时间"重做一轮核心循环。

### 方案 B：软上限 + 叙事时钟（中改，推荐）

保留 `age` / `lifespan` 双字段，但明确规定：

- 自然衰老是唯一被动时钟，按人界纪年推进年龄；
- 闭关是主动预支，推进年龄；
- 副本、战败、重伤扣寿元上限，统一走"折寿"结算与文案；突破失败不折寿（v10 修订）；
- 寿元低于阈值时预警，归零直接判死，不设虚弱免死（v10 修订）；
- 所有死亡入口统一经过同一个结算器，保证故事、日志与通知一致。

- 优点：改动集中在寿元规则层与少量 UI，存量存档天然兼容，风险可控。
- 缺点：仍保留两个字段，需要靠统一入口避免再次分裂。
- 适用：希望让寿元"有存在感"但不想重做全经济。

### 方案 C：纯叙事时钟（轻改）

寿元只作为境界突破的时间门槛与死亡倒计时，不参与任何玩法成本；副本不再生成寿元成本，寿元丹仅用于延长角色寿命。自然衰老保留为唯一的被动消耗，闭关改为不推进年龄，只消耗灵气与时间窗口。

- 优点：最小改动，清除 LLM 生成寿元成本的不确定性，并消除"现实时钟 + 闭关预支"的双重扣减。
- 缺点：寿元仍不具备策略深度，只是背景设定；闭关不再有"燃烧寿命换修为"的取舍。
- 适用：当前优先级是稳定与内容填充，而不是系统深化。

### 方案 D：统一人界纪年时钟（v3 新增，角色私有时钟）

把"年/月/日"作为唯一时间单位，现实小时只保留为底层调度，不出现在玩法公式与玩家文案中。

- **时钟归属**：每个角色拥有私有纪年，`角色纪年 = 诞辰纪年 + age + 年内余量`；不闭关时与 `world_clock` 世界纪年同步，闭关即时跳年，角色纪年领先世界纪年。世界纪年只累计服务端运行时长，停机暂停（v15）。
- **单位换算**：现实 12 小时运行时长 = 1 游戏年、1 小时 = 1 游戏月、2 分钟 = 1 游戏日。
- **历练**：由"每现实小时 0.008 日预算、上限 24 小时"改为"每游戏月 0.008 日预算"，公式数值等价；每满 1 年由后台自动结算并写入历练日志，玩家不再手动领取，也不再按 2 年封顶累积。
- **挂机/讨伐**：6 小时 → 6 月（0.5 年）。
- **市场刷新**：2 小时 → 2 月。
- **灵气恢复**：6 分钟 → 3 日。
- **突破**：固定耗时 1 年，与现有剧情文案 `yearsSpent: 1` 对齐。
- **世界侧系统**（宗门、市场、竞技、活动）继续使用全局世界纪年，不受角色跳年影响。

- 优点：所有玩法共享一套时间语言；闭关、衰老、历练从同一锚点推导，可合并 `aging_synced_at` 与 `last_yield_at` 的语义；修为数值零改动，风险集中在展示层与一次迁移。
- 缺点：同屏玩家角色纪年可能不同，需要在 UI 上明确区分"此身纪年"与"世界纪年"；历练结算间隔从 1 小时拉长到 12 小时，日活手感改由历练日志与通知承担。
- 适用：确定保留即时闭关、又不希望出现小时/年/轮三套口径。

## 7. 推荐方案 B / D 的规则与数值框架

### 7.1 规则定义

- `age`：角色已经活过的年数，由自然衰老（现实 12 小时运行时长 = 1 游戏年）、闭关年数与突破固定 1 年共同推进。
- `lifespan`：这一世寿元上限。大境界突破时抬到目标境界的基础寿命（`max(当前, 基础)`），延寿丹药/灵果、宗门恩赏在此基础上叠加。
- `remaining = lifespan - age`：UI 与提示统一使用"剩余寿元"，只展示游戏年，不直接换算现实可存活天数。
- 折寿：副本、战败、重伤等直接减少 `lifespan`，并在玩家日志中记录来源；战败折寿见 3.7。突破失败不折寿。
- 死亡：唯一入口是寿元耗尽——`remaining <= 0` 时按来源统一判死（自然衰老、闭关、突破、副本、战败折寿），不再设"寿元将尽"可救治缓冲；战败折寿触底归类为自然死亡中的特殊战斗死亡。
- 自然衰老统一入口：cron、闭关、突破、副本、战斗五条路径都调用同一结算器，统一故事、事件、通知与死亡来源。

### 7.4 UI 与提示

- 角色面板：`剩余 {remaining} 年 / 上限 {lifespan} 年（已活 {age} 年）`
- 静室：闭关确认显示"本次消耗 {years} 年，闭关后剩余 {remaining - years} 年"
- 副本选项：寿元成本使用"折寿 {value} 年"
- 突破确认：显示"本次突破消耗 1 年，突破后剩余 {remaining - 1} 年"；失败同样消耗 1 年
- HUD：纪年旁边只显示"余寿 X 年"，不展示现实天数；玩家可自行按 12 小时运行 = 1 年换算
- 寿元低于 20% 时提醒；归零即按来源判死，不再进入"寿元将尽"状态
- 闭关确认需要显示单次年限上限、闭关后剩余寿元，以及可能触发死亡的风险提示

### 7.5 统一人界纪年的时间口径（方案 D）

已定决策：

1. 纪年归属：**角色私有时钟**。闭关即时推进角色纪年，HUD 显示"此身纪年"，世界纪年单独展示或作为环境信息。
2. 历练节奏：**每满 1 年由后台自动结算一次并写入日志，不再由玩家手动领取**；世界时钟停机暂停，正常每次 tick 结算 1 年，仅进程卡顿或 tick 被跳过时最多补算 2 年。
3. 自然衰老保留为游戏核心机制，现实 12 小时运行时长 = 1 游戏年是既定节奏。
4. 玩家界面只显示年/月/日，不直接显示现实可存活天数。

规则：

- `角色纪年 = 诞辰纪年 + age + 年内余量`；`诞辰纪年 = 当前世界纪年 − age`（存量回填口径，之后闭关才产生偏移）。
- 年内余量由 `aging_synced_at` 推导，保留不足一年的零头，月/日由此换算。
- 所有玩家可见的时间文案只使用"年/月/日"，不再出现"小时""轮""现实天数"；运维日志、邮件保留期等非玩法语义可继续用现实时间。
- 历练、衰老、挂机共用同一"角色时间锚点"，不再各自从 `last_yield_at`、`aging_synced_at` 独立推导。
- 副本、战斗仍可按"轮"结算，但对外展示与成本统一折算为年/月/日。

单位换算：

| 单位 | 现实时长 | 用途 |
| --- | --- | --- |
| 1 游戏年 | 12 小时 | 历练、闭关、寿元、突破 |
| 1 游戏月 | 1 小时 | 历练收益按整月累积（满 1 年自动结算）、市场刷新 |
| 1 游戏日 | 2 分钟 | 灵气恢复、短耗时行为 |

副作用（需一并写入验收）：

- 历练结算间隔由 1 小时变为 12 小时，日活手感下降；结算改为后台自动完成后，用历练日志、邮件与关键事件通知承接回流。
- 突破开始消耗 1 年，炼气可用寿元减少约 1 年。

### 7.6 闭关收益重定价（v3 新增，v10 定稿）

4.2 节测算显示：同按 1 游戏年折算，历练产出约为闭关的 16.7 倍。v10 已定目标：**闭关年收益不低于同期正常历练的 80%**；闭关仍不产灵石、道具与掉落，只产修为与感悟。

旋钮：`RETREAT_EXP_BUDGET.dailyFractionPerYear`（现 0.005）。200 年批次含倍率后实际系数约 ×1.151（年限 1.1835 × 随机 0.95 × 顿悟期望 1.025）。历练基线为 9.6%/年，因此闭关目标为 ≥7.68%/年，对应 `dailyFractionPerYear ≈ 0.067`（×13.4）。

| 方案 | 系数 | 闭关/年（含倍率） | 闭关占历练 | 炼气一生覆盖 | 化神一生覆盖 | 一次 200 年等效历练 |
| --- | --- | --- | --- | --- | --- | --- |
| 现状 | 0.005 | 0.58% | 6% | 15% | 16% | ≈ 6 天 |
| ×4 | 0.02 | 2.30% | 24% | 61% | 65% | ≈ 24 天 |
| ×6 | 0.03 | 3.45% | 36% | 91% | 97% | ≈ 36 天 |
| ×10 | 0.05 | 5.76% | 60% | 152% | 162% | ≈ 60 天 |
| **×13.4（v10 定稿）** | **0.067** | **7.71%** | **80.3%** | **204%** | **217%** | **≈ 80 天** |

> 表中「一生覆盖」按 2.5 的剩余寿元（炼气 ≈82 年、化神 ≈1982 年）计算；「闭关占历练」= 闭关年收益 / 历练 9.6%/年。

定稿说明：

1. 取 ×13.4 是满足「不低于历练 80%」的最低档，保留历练在灵石、感悟、掉落与不烧寿元上的优势。
2. 炼气一生闭关覆盖约 204%，化神约 217%，寿元不再是纯闭关的硬约束；必须与 B1 压缩曲线、单次闭关封顶和副本/战败折寿一起打包，否则寿元会重新变成冗余数字。
3. 与 B1（化神 800 年）打包后，化神一生覆盖约 87%，仍接近一次完整需求；若希望保留更强稀缺性，可把 B1 进一步下调或降低闭关系数。
4. 拉满灵根/养元丹/宗门功法（约 ×3）后极限闭关约 23.1%/年，高于历练；这是资源换修为的正反馈，但闭关仍不产灵石与道具。
5. 瓶颈期减半后约 3.86%/年，仍显著低于历练，保留"70% 后转历练/突破"的引导。

连带事项：

- 灵气成本（200 年 = 80 灵气）在收益 ×13.4 后明显偏低，需要同步上调，否则闭关成为无脑最优；建议按收益倍数同比提高或单独重定价，具体待数值校准。
- 若寿元维持境界基础寿命（化神 2000 年），×13.4 下化神一生覆盖约 217%；与 B1 曲线（化神 800 年）打包后回落到约 87%。
- 改动文件：`packages/game-content/src/cultivation/cultivationExpGain.ts`，同步更新该常量上方注释；仅调常量，不改公式与倍率。

### 7.7 闭关单次年限与防自杀保护（v10 新增）

v10 已定：闭关继续推进 `age`，但必须限制各境界单次闭关年限，避免玩家用一次闭关把剩余寿元直接打空。

规则：

- 单次年限 ≤ `min(200, 当前境界基础寿命 × 20%)`。
- 闭关后必须保留至少 `max(1, 当前境界基础寿命 × 10%)` 的剩余寿元，否则直接拒绝。
- 不足 1 年按 1 年计；UI 默认填当前允许的最大值，剩余寿元低于 20% 时二次确认。
- 该上限只约束单次，不限制总闭关年数；自然衰老仍持续消耗。

| 境界 | 单次上限 | 闭关后最低余寿 |
| --- | --- | --- |
| 炼气 | 20 | 10 |
| 筑基 | 40 | 20 |
| 金丹 | 100 | 50 |
| 元婴 | 200 | 120 |
| 化神 | 200 | 200 |
| 炼虚 | 200 | 300 |
| 合体 | 200 | 400 |
| 大乘 | 200 | 500 |
| 渡劫 | 200 | 800 |

实现落点：`RetreatApplicationService` 在调用 `performCultivation` 前校验；`CultivationEngine` 保持纯函数，由服务层传入已校验的年限。验收需覆盖「刚好触底被拒绝」「跨境界上限变化」「剩余寿元低于最低值时不可闭关」。

### 7.8 历练体系设计（v12 新增，草案）

**定位**：历练是把现实等待时间换成修为与资源的主路径，也是自然衰老之外唯一「不主动操作也有产出」的入口。历练的成本不是灵气，而是寿元：历练的每 1 个游戏年都由自然衰老推进 1 岁；历练结算本身不再重复 `age += years`。

#### 7.8.1 按年阶段结算

- 1 游戏年 = 1 个历练阶段；每满 1 年由后台自动结算 1 次，不等待玩家领取，结算结果写入历练日志。
- 不足 1 年不结算，零头保留在角色时间锚点，下个 tick 继续累积。
- 每个阶段的事件、战斗与掉落由服务端在该年结算时一次性掷出。随机种子必须由服务端事实派生：`cultivatorId + 锚点 + 阶段序号`；客户端的 `requestId` 只做幂等，不能参与随机，避免改参数重掷。
- 自动结算与自然衰老共用同一个世界 tick：先结算已完成年份的历练，再推进 `age`；正常在线角色每次 tick 只结算 1 年。
- 停机期间 `world_clock` 暂停，恢复后从暂停点续走，因此维护不会产生历练积压；只有进程卡顿或 tick 被跳过时，单次 tick 最多补算 2 年。
- 玩家离线不影响结算，也不会因为长期未登录而丢失历练收益；上线后在日志中查看逐年结果。

#### 7.8.2 年度收益预算（沿用现状基线）

历练每年总产出维持现有量级，事件只负责「怎么发生」，不额外增发：

| 境界 | 灵石/年 | 修为/年 | 感悟/年 | 材料槽/年 |
| --- | --- | --- | --- | --- |
| 炼气 | 1,680 | 96 | 约 18 | 4 |
| 筑基 | 3,360 | 172.8 | 约 18 | 4 |
| 金丹 | 6,720 | 307.2 | 约 18 | 4 |
| 元婴 | 13,440 | 537.6 | 约 18 | 4 |
| 化神 | 26,880 | 864 | 约 18 | 4 |
| 炼虚 | 53,760 | 1,344 | 约 18 | 4 |
| 合体 | 80,640 | 2,016 | 约 18 | 4 |
| 大乘 | 107,520 | 2,880 | 约 18 | 4 |
| 渡劫 | 215,040 | 4,032 | 约 18 | 4 |

- 灵石按 `REALM_YIELD_RATES × 12 小时 × 1.4`（随机均值）计算，修为为日预算的 9.6%/年，均为现状口径。
- 遗迹、妖兽、抢夺的额外收益只能从当年预算内分配，或占用材料槽；不允许事件层凭空生成灵石与道具。
- 稀有掉落（灵印、图纸、稀有材料）有独立的年度次数上限，建议每年最多 1 次，且不高于当年灵石预算的 50%。

#### 7.8.3 事件池与其他玩家遭遇

| 事件 | 基础权重 | 是否战斗 | 主要产出 | 寿元风险 |
| --- | --- | --- | --- | --- |
| 行旅拾遗 | 40% | 无 | 小额灵石、普通材料 | 无 |
| 山野妖兽 | 25% | PVE | 兽材、材料、修为 | 败则按 PVE ×1.0 折寿 |
| 残破遗迹 | 15% | PVE 守卫或属性检定 | 灵石、稀有材料、概率灵印/图纸 | 败则按 PVE ×1.0 折寿 |
| 同道相逢 | 12% | 可选切磋 | 感悟、情报、以物易物 | 切磋 ×0 |
| 劫修拦路 | 8% | PVE | 反夺灵石、材料 | 败则按 PVE ×1.0 折寿 |
| 野外夺宝 | 0%（需开关） | 野外 PVP | 转移败方灵石/可交易材料 | 败方按 ×1.0 折寿 |

- 「遇到其他玩家」采用异步快照：结算时读取对方的公开战力、外观与行囊快照，不要求双方同时在线；实时切磋仍走竞技场。
- 同道相逢的切磋与交易属于社交事件，不产生寿元损失；野外夺宝是唯一涉及玩家间资源转移的事件。
- 权重为初始建议值，按境界与区域可再分池；炼气～筑基不进入「劫修拦路」与「野外夺宝」池。

#### 7.8.4 灵石与道具从哪来

三种来源并存，按事件池分配，而不是所有产出都写成「打怪掉落」：

| 来源 | 对应事件 | 产出范围 | 占灵石产出（建议） | 占道具产出（建议） |
| --- | --- | --- | --- | --- |
| 路上捡的 | 行旅拾遗 | 小额灵石、普通材料 | 35% | 10% |
| 遗迹/妖兽爆的 | 残破遗迹、山野妖兽、劫修拦路 | 灵石、材料、兽材、稀有掉落 | 55% | 85% |
| 其他玩家身上抢的 | 野外夺宝 | 仅转移灵石与可交易材料 | 10%（转移，不增发） | 5%（转移） |

约束：

- 抢夺只转移，不生成；单次不超过败方携带灵石的 10%，且不得夺取装备、灵印、绑定物与任务物品。
- 「露财」默认关闭；未开启时不进入野外夺宝池，避免被动挨抢。开启后主动承担被抢风险，并换取更高的灵石收益权重。
- 所有道具必须走 `DropPool` / `rewardId`；LLM 只能写事件文案，不能生成奖励 ID、数量或战斗结果。

#### 7.8.5 历练战斗与折寿

- 事件触发战斗后进入 V6 战斗内核，元数据新增 `sourceType: 'yield-encounter'`（或复用 `wild-encounter` 的生成器与掉落池，二选一在落地时定）。战斗结果只由内核判定，事件层不能直接判负或扣血。
- PVE 战败按 3.7 的 PVE 常规 ×1.0 折寿；不判死，折寿触底时由统一寿元扣除结算器判死，来源 `battle_defeat`，归类为自然死亡中的特殊战斗死亡。
- 野外 PVP 按 v11 规则 ×1.0，不享受保护；同道切磋 ×0。
- 战斗胜利的修为与战利品从当年预算内发放，不额外增发；同一阶段最多触发 1 场战斗，避免连续战斗放大方差。
- 折寿日上限、单次 200 年上限、幂等键与 3.7 完全共用。

#### 7.8.6 与闭关、副本的边界

- 历练：9.6%/年，有灵石、材料、感悟与战斗风险，后台按年自动结算。
- 闭关：7.71%/年（历练的 80.3%），只产修为与感悟，不产道具，无战斗风险，可一次推进到境界上限。
- 副本：主动解谜与高风险高产出，不给历练专属稀有掉落；历练也不生成副本钥匙或剧情节点。
- 三者的时间成本都记在同一本寿元账上，不允许任何一条路径绕开自然衰老。

#### 7.8.7 实现落点

| 层 | 位置 | 改动 |
| --- | --- | --- |
| 域 | `packages/game-domain/src/yield/` | 新增 `YieldStageEvent`、结果与掉落模型 |
| 规则 | `packages/game-rules/src/yield/` | 新增 `resolveYieldStage` 纯函数：事件抽取、预算分配、战斗交接、折寿标记 |
| 内容 | `packages/game-content/src/yield/events.ts` | 事件权重、境界/区域分池、年度稀有次数 |
| 服务 | `apps/api/src/cultivator/application/YieldApplicationService.ts` | 改为后台按年自动结算、事务写资源、发起历练战斗、幂等 |
| 任务 | `apps/api/src/runtime/jobs/internalCron.ts` | 与自然衰老同一 tick：先结算历练，再推进 `age`；停机暂停，卡顿时单次最多补算 2 年 |
| 数据 | `cultivators.last_yield_at` + 新增 `cultivator_yield_logs` | 日志表字段：`cultivator_id`、`stage_year`、`location_id`、`event_key`、`summary`、`payload jsonb`、`created_at`；**永久保留**，按 `(cultivator_id, stage_year)` 建索引 |
| 人生总结 | `GET /api/cultivator/yield/life-summary` | 按年/地点/事件聚合，统计一生历练地点、战斗次数、折寿、主要产出；死亡与转世页复用 |
| 前端 | `apps/web/src/components/feature/cultivator/YieldCard.tsx` | 改为「历练日志」年表：逐年展示事件、战斗、折寿与净收益，不再有领取按钮 |

**验收要点**

1. 服务端累计运行满 12 小时后的第一个 tick 自动结算 1 年，无需玩家在线或点击；结算结果出现在历练日志中。
2. 重复 tick、服务重启、同一角色并发结算不重复发奖、不重掷事件，日志只产生一条记录。
3. 停机 30 天后恢复：世界时钟从暂停点续走，不补算、不扣寿元，历练日志也不新增停机期间年份。
4. 事件只重分配当年预算：全年灵石/修为/材料总量与 7.8.2 基线一致，误差只来自随机系数。
5. 历练 PVE 战败按 3.7 扣 `lifespan`；折寿触底生成统一死亡记录；切磋不折寿。
6. 抢夺只转移不增发，单次与每日上限生效，装备/灵印/绑定物不可被夺。
7. 事件文案与战斗结果由服务端事实生成，LLM 输出不能改变奖励数量或胜负。

#### 7.8.8 仍需决策

- 事件权重与各境界分池是否按上表执行。
- 野外夺宝是否保留、是否默认关闭「露财」、是否允许转移材料。
- 历练战斗复用 `wild-encounter` 还是新增 `yield-encounter` 元数据。
- 是否让 LLM 参与事件文案；若参与，只做叙事，不做数值。

### 7.9 历练地点体系与重构方案（v13 新增，草案）

**目标**：把历练从「全地图同一公式的挂机收益」改成「地点驱动的年度经历」。玩家先在地图上选一处地点，历练的事件、产出、战斗与 PVP 风险都由该地点决定；现有按小时一次性结算的 `YieldApplicationService` 需要整体重构。

#### 7.9.1 地点模型

复用现有世界地图，不新造一套坐标：

- 主节点 `MapNode`：区域/城镇，字段含 `id/name/region/realm_requirement/tags/market_config/dungeon_config`（`packages/game-domain/src/world/map.ts` 第 72～101 行）。
- 卫星节点 `SatelliteNode`：遗迹、荒野、资源点、灵兽栖息地，带 `parent_id` 与 `type`（同文件第 84～101 行；`map.json` 已有「遗迹/荒野/资源点/灵兽栖息地」等类型）。
- 读取入口沿用 `packages/game-content/src/world/map.ts` 的 `getMapNode`、`getNodesByRegion`、`getSatellitesForNode`。

新增历练地点注册表 `packages/game-content/src/yield/locations.ts`，只引用地图节点，不复制名称与描述：

```ts
interface TrainingLocation {
  nodeId: string;                 // 必须存在于 map.json
  kind: 'town' | 'wilderness';
  eventPool: string;
  danger: 0 | 1 | 2 | 3;
  stoneMultiplier: number;
  expMultiplier: number;
  safeZone: boolean;              // 战败后退回的安全区
  adjacent: string[];             // 相近地点，供 PVP 相遇
  tags: string[];                 // 采药 / 矿脉 / 坊市 / 妖兽 …
}
```

#### 7.9.2 地图选点

- 复用 `/game/map-v2` 与 `DungeonMapSelector` / `MapNodeCard` 的交互（`apps/web/src/routes/game/dungeon/components/DungeonMapSelector.tsx` 第 23～44 行）：地图点选 → 地点卡 → 确认历练。
- 地图新增「历练」模式，只高亮已注册为 `TrainingLocation` 的节点；地点卡显示境界门槛、危险度、事件倾向、预计年收益与 PVP 风险。
- 历练页顶部显示当前地点，提供「更换地点」入口；未选地点时默认 `越国·太岳山脉`（新手区），并提示玩家主动选择。
- 切换规则：历练由后台自动结算，玩家随时可以换点；切换前已完成的年份按旧地点结算完毕，新地点从下一个未结算年份生效，避免中途换点套利。
- 解锁条件：满足 `realm_requirement` 即可；危险野外可要求前置地点首次到达。

#### 7.9.3 城镇与野外的事件池

| 地点类型 | 事件 | 权重 | 主要产出 | 战斗 | PVP |
| --- | --- | --- | --- | --- | --- |
| 城镇 | 行旅拾遗 | 30% | 小额灵石、普通材料 | 无 | 无 |
| 城镇 | 坊市采买 | 20% | 用灵石购买材料/丹药（有折扣） | 无 | 无 |
| 城镇 | 打工/护送 | 25% | 灵石 + 少量修为 | 无 | 无 |
| 城镇 | 悬赏任务 | 15% | 灵石、材料、声望 | 极低概率 PVE | 无 |
| 城镇 | 同道相逢 | 10% | 感悟、情报、可选切磋 | 切磋 ×0 | 无 |
| 野外 | 采集拾遗 | 25% | 该地图特产材料 | 无 | 无 |
| 野外 | 山野妖兽 | 30% | 兽材、材料、修为 | PVE ×1.0 | 有 |
| 野外 | 残破遗迹 | 15% | 灵石、稀有材料、图纸 | PVE ×1.0 或属性检定 | 有 |
| 野外 | 劫修拦路 | 15% | 反夺灵石、材料 | PVE ×1.0 | 有 |
| 野外 | 同道/夺宝 | 15% | 切磋或转移资源 | 切磋 ×0 / 夺宝 ×1.0 | 有 |

- 城镇以「捡到、买到、打工、任务」为主，不以打怪掉落为主；「采买」是灵石换材料，不增加净灵石。
- 野外产出绑定地图：材料池取该节点/区域的物种、灵脉、灵植与矿脉标签，可直接复用现有 `wild-encounter` 生成器与 `DropPool`。
- 事件权重写在地点配置里，不写死在服务层；同一 `kind` 可以有多个事件池。

#### 7.9.4 地点乘区

7.8.2 的年度预算仍是总量基线，地点只做乘区与分配：

| 地点类型 | 灵石 | 修为 | 材料 | 风险 |
| --- | --- | --- | --- | --- |
| 城镇 | ×0.9 | ×0.9 | 采买/任务为主 | 低 |
| 野外普通 | ×1.0 | ×1.0 | 地图特产 | 中 |
| 野外危险 | ×1.15 | ×1.1 | 稀有材料概率提高 | 高，战斗与折寿更多 |

乘区只影响当年预算分配，不突破单次 200 年折寿上限与每日 10% 上限。

#### 7.9.5 同地点 PVP 相遇

- 相近判定：同一 `nodeId`，或 `adjacent` 显式配置的相邻地点；跨区域不匹配。
- 只有双方都在野外地点、且都开启「露财」时，才进入「野外夺宝」；否则只触发「同道相逢」（切磋/交易）。
- 异步快照：读取对方在该地点的公开战力、外观与行囊快照，不要求同时在线。
- 境界保护：炼气～筑基不进入夺宝池；同地点被同一对手重复击败，第 2 次起折寿减半（沿用 3.7 防滥用）。
- 切磋全境界 ×0，实时对战仍走竞技场；历练内可拒绝应战，拒绝不产生损失。
- 战败退回安全区（v14）：历练 PVP 败方除按 ×1.0 折寿外，自动把 `training_location_id` 切换到最近的安全区（城镇/宗门驻地），本阶段剩余预算按安全区事件池结算，不再触发战斗与 PVP；下一阶段继续留在安全区，玩家可手动返回野外。
- 安全区选择：优先同 `region` 内标记为 `safeZone` 的城镇节点；没有则回落到 `越国·太岳山脉`。日志记录「败退：A → B」。
- 城镇、宗门驻地与安全区强制无 PVP。

#### 7.9.7 接口草案

- `GET /api/cultivator/training-locations`：返回可选地点（id、名称、类型、境界门槛、危险度、乘区、事件预览）。
- `PUT /api/cultivator/training-location`：设置地点，从下一个未结算年份生效；已结算年份不受影响。
- `GET /api/cultivator/yield/logs`：分页返回历练日志（年份、地点、事件、战斗、折寿、净收益）。
- `GET /api/cultivator/yield/preview`：当前地点下一阶段的预期收益与风险（可选）。
- 不再提供 `POST /api/cultivator/yield` 手动领取入口；保留旧路由时只返回"已改为自动结算"的提示。

#### 7.9.8 验收要点

1. 地图选点后，历练页与日志都使用该地点；换点后已结算年份仍按旧地点，未结算年份按新地点。
2. 城镇不触发野外夺宝与山野妖兽；野外产出引用对应地图的掉落池与物种。
3. 同节点或相邻节点、双方开启「露财」才触发夺宝；跨区域不匹配；城镇不匹配。
4. 历练 PVP 败方自动退回最近安全区，本阶段剩余预算按安全区结算，日志有「败退」记录。
5. 旧角色没有地点时默认太岳山脉，不报错，`last_yield_at` 不丢失。
6. 事件种子可由服务端复算，刷新与消息重投不重掷。
7. 战败折寿、触底判死、切磋 ×0 与 3.7 完全一致。
8. 无需领取：玩家整年不登录，日志仍逐年产生，资源余额与日志一致。

#### 7.9.11 配置结构与维护规则

```ts
type TrainingPvp = 'none' | 'spar' | 'loot';

interface TrainingLocation {
  nodeId: string;
  kind: 'town' | 'wilderness';
  eventPool: string;
  danger: 0 | 1 | 2 | 3;
  stoneMultiplier: number;
  expMultiplier: number;
  safeZone: boolean;
  pvp: TrainingPvp;
  adjacent: string[];
  tags: string[];
  lootTable: {
    common: string[];
    specialty: string[];
    rare: string[];
  };
  services?: Array<'market' | 'work' | 'bounty' | 'auction'>;
  unlock?: { realm: RealmType; visitedNodeId?: string };
}
```

- `pvp: 'loot'` 只允许出现在危险野外；普通野外最多 `spar`；城镇、宗门与安全区一律 `none`。
- `rare` 每年最多 1 件；`loot` 不能从玩家身上夺走 `rare`、装备、灵印与绑定物。
- 新增地点只改内容注册表与地图，不改服务层；配置必须通过 zod 校验，并引用合法的 `map.json` 节点与 `DropPool` ID。
- 事件池按 `kind + tags` 组合，不按具体地点写死；同标签地点共享模板，再覆盖特产与权重。

#### 7.9.12 日志永久保留与人生总结

- `cultivator_yield_logs` 永久保留，不设 TTL；按 `(cultivator_id, stage_year)` 建索引，按年查询与聚合。
- 死亡或转世时生成「人生总结」：历练足迹（去过的地点与年份）、战斗与败退次数、累计折寿、主要机缘与稀有掉落、最常驻地点。
- `GET /api/cultivator/yield/life-summary` 直接聚合日志，不额外建汇总表；如需性能再物化。
- 日志可见范围：角色所有者与 admin；其他玩家只能看到公开足迹，不展示行囊与收益细节。

### 8.2 验收标准

1. 纯规则单测覆盖：寿元增减、折寿、死亡阈值、突破切换境界基础寿命、延寿递减与单世上限。
2. 九个境界各跑通一次完整流程：初始生成、闭关、突破、副本折寿、死亡/转世。
3. 存量角色读取后不丢失寿元数据；旧存档年龄大于新上限时不静默判死，迁移脚本保留旧值或给出明确选择，并记录口径。
4. 浏览器检查角色面板、静室确认、副本结算三处寿元文案一致；玩家界面不出现现实天数。
5. 专项验证 LLM 副本选项不会生成超过上限或负数的寿元成本。
6. 自然衰老 tick：连续运行 12 小时只 +1 岁、锚点保留不足一年的零头、重复调用不重复推龄、判死后有统一故事/事件；停机 30 天不增加年龄。
7. 确认存量角色 `aging_synced_at` 默认 `now()` 的语义：是否补算上线前的时间，并在验收记录中写明。
8. 战败折寿：同阶重伤/濒死分别按基准值 ×1/×2 扣减 `lifespan`；折寿触底由寿元扣除判定为自然死亡中的特殊战斗死亡；同一 `battleId` 重复投递不重复扣。
9. 闭关单次上限：各境界按 7.7 拒绝超限；闭关后最低余寿校验生效；不能通过一次闭关直接寿尽。
10. 闭关年收益达到同期历练的 80% 以上，且闭关不产灵石、道具与掉落。
11. PVE 战败全部折寿；切磋/友谊赛全境界 ×0；野外 PVP 与生死决斗按对应类型倍率正常折寿。
12. 死亡统一：自然衰老、闭关、突破、副本、战败折寿触底均生成死亡故事与邮件/站内通知，来源字段正确。
13. 突破固定耗时 1 年：成功与失败都 `age += 1`、历史 `years_spent: 1`，结算页与剧情文案一致；因突破消耗导致寿尽时同样走统一死亡结算。
14. 运行时钟：停机 30 天后重启，世界纪年与角色年龄都不增加；连续运行满 12 小时只结算 1 年。
15. 历练日志永久保留，可生成人生总结；重启与消息重投不重复写日志。

### 8.3 数据与内容风险

- 若采用 B1 曲线，存量高境界角色的 `lifespan` 可能高于新曲线，需要归档口径或按旧值保留，不可直接回写。
- 延寿丹方涉及炼丹评分与药性权重，调整延寿值会牵动丹方经济。
- 副本寿元成本由 LLM 生成，提示词与后端上限必须同时调整，否则会出现"文案说折寿 10 年、实际扣 1 年"的错位。
- 灵兽寿元与人物寿元的 UI 共用"寿命"字样，v10 已定统一改名为「寿元」，并保留各自恢复规则。
- 纪年改为运行时钟后，换算率（12 小时 = 1 年）仍是全局常量；但停机不计时意味着服务器长期不可用会冻结全服年龄，需要监控运行时长与落盘间隔，避免崩溃丢失超过 5 分钟。
- 世界时钟落盘与 runtime leader 绑定；多实例切换时必须保证只有一个写者，否则会出现时间跳变。
- 历练日志永久保留会持续增长（每个活跃角色约每 12 小时 1 行），需要按年归档或分区，查询只走 `(cultivator_id, stage_year)` 索引。
- `aging_synced_at` 在迁移 0073 中默认 `now()`，上线前创建的角色不会补算历史时间；若要追溯，需要单独回填。
- `runWorldAgingTickJob` 在单个事务中循环更新所有落后的 active 角色，角色规模增大后存在长事务与锁风险，需要分批或加索引。

## 9. 决策记录与剩余参数

**A/B/C/D 是什么（见第 6 节）**

- **A 寿元货币化（大改）**：剩余寿元变成通用资源，闭关、副本、探索、赶路等都按年计价，寿元可交易、抵押。改动面最大。
- **B 软上限 + 叙事时钟（中改）**：保留 `age` / `lifespan` 双字段，自然衰老是唯一被动时钟，闭关主动预支年龄，副本/战败折寿，死亡统一结算。
- **C 纯叙事时钟（轻改）**：寿元只做境界门槛与死亡倒计时，不参与玩法成本；闭关不推进年龄。
- **D 统一人界纪年时钟**：年/月/日成为唯一时间单位，每个角色有私有纪年，闭关即时跳年；是 B 的底层时间实现。

按本轮回答，A（货币化）与 C（闭关不推进年龄）已排除；保留自然衰老 + 统一角色时钟，等价于 **B + D**。B 原方案中的「寿元将尽虚弱免死」与「突破失败折寿」已由本轮决策覆盖（见 9.1）。若没有异议，实施按 B+D 执行。

### 9.1 已定（v10，v11/v14/v15 补充）

1. 寿元定位：**B + D**，保留自然衰老与统一角色时钟；不做寿元货币化，不做纯叙事。
2. 自然衰老：保留为游戏核心机制，现实 12 小时**服务端运行时长** = 1 游戏年。
3. 闭关：继续推进 `age`；单次年限按 7.7 按境界封顶，并保留最低余寿，避免自杀性闭关。
4. 死亡通知：自然老死需要死亡故事、邮件/站内通知与前世记录，不再静默判死。
5. 现实天数：不向玩家直接展示，只显示游戏年；玩家可自行按 12 小时运行 = 1 年换算。
6. 境界范围：本轮直接开放到渡劫，不做入口封顶。
7. 突破失败：不折寿；已投入材料与时间就是成本。
8. 前世加成：道友侧不做继承计算；依赖主站，目前无建设，仅预留 `generation` 参数。
9. 延寿丹：加入同丹药递减（`0.85^(n-1)`，最低 20%）与单世累计上限（建议 100% 当前境界基础寿命）。
10. 灵兽寿元：统一「寿元」命名与剩余量展示；保留可恢复、固定上限、战死扣 50 的规则。
11. 闭关收益：年收益不低于同期历练的 80%（`dailyFractionPerYear ≈ 0.067`，×13.4）；闭关不产灵石、道具与掉落。
12. 战败折寿：全部 PVE 生效；切磋/友谊赛全境界 ×0。
13. PVP 保护范围（v11）：仅切磋/友谊赛受保护；野外 PVP 与生死决斗不享受保护，按对应类型倍率正常折寿。
14. 折寿触底：不再进入「寿元将尽」缓冲；由寿元扣除判定为自然死亡中的特殊战斗死亡，来源标记 `battle_defeat`。
15. 突破耗时（v11）：固定消耗 1 年，成功与失败都推进 `age`，历史记录 `years_spent: 1`，随本轮上线。
16. 历练结算（v14）：后台按年自动结算，玩家无需领取；历练 PVP 败方自动退回最近安全区继续历练。
17. 历练地点（v13/v15）：玩家从地图选择城镇或野外地点，事件与产出按地点事件池、标签与掉落池决定。
18. 历练日志（v15）：永久保留，用于死亡/转世时生成人生总结。
19. 世界时钟（v15）：改用服务端运行时钟，停机暂停、启动续走，维护不再消耗寿元与历练年份。

### 9.2 仍需数值校准

- 延寿丹单世上限取 100% 基础寿命、递减 0.85/最低 20% 是否合适。
- 野外 PVP 与生死决斗的类型倍率是否都取 ×1.0，还是生死决斗另设更高倍率。
- 7.6 的 ×13.4 与 B1 曲线是否同期上线；若不同期，先上哪一个。
- 闭关灵气成本在收益 ×13.4 后如何上调。

- T4 与 T5 的灵根档相同，都是单灵根；T5 的差异来自「满献祭」的道装、技能数量与物资，不来自根数。
- 目标 OPI 是档位基准，角色定位会在此基准上做小幅偏移，见第 15 节。
- 所有档位仍从炼气初期（5 级）开始，不因高献祭档直接跳到高境界。

## 14. 灵根设计

### 14.1 原神元素到灵根的映射

原神只有七元素，道友有金木水火土风雷冰八灵根。映射如下：

| 原神元素 | 首灵根 | 说明 |
| --- | --- | --- |
| 火 Pyro | 火 | 正灵根 |
| 水 Hydro | 水 | 正灵根 |
| 冰 Cryo | 冰 | 变异灵根 |
| 雷 Electro | 雷 | 变异灵根 |
| 风 Anemo | 风 | 变异灵根 |
| 土 Geo | 土 | 正灵根 |
| 木 Dendro | 木 | 正灵根 |
| 无对应 | 金 | 只作为旁支灵根，不设「金系原神角色」 |

**首灵根永远是角色自身元素。** 金灵根只通过旁支出现，用来体现剑修、器修与「金主杀伐」的世界观，不允许覆盖角色的原神元素。

### 14.2 旁支灵根顺序

为了让 36 个角色可批量配置、又有稳定的五档结构，旁支按元素统一给定，后续可按角色微调：

| 元素 | 第 1 灵根（首） | 第 2 灵根 | 第 3 灵根 | 第 4 灵根 |
| --- | --- | --- | --- | --- |
| 火 | 火 | 金 | 木 | 土 |
| 水 | 水 | 木 | 金 | 土 |
| 冰 | 冰 | 水 | 金 | 木 |
| 雷 | 雷 | 金 | 火 | 土 |
| 风 | 风 | 木 | 水 | 金 |
| 土 | 土 | 金 | 火 | 水 |
| 木 | 木 | 水 | 土 | 金 |

生成时按档位截取：

- T1：取全部 4 个；
- T2：取前 3 个；
- T3：取前 2 个；
- T4 / T5：只取首灵根。

这样每个角色的灵根谱都是确定的，随机只发生在灵根强度与技能上。

### 14.3 灵根强度与标签

直接复用现有生成器，不新增根数上限：

| 根数 | 基础上限 | 变异加成 | 最终上限 |
| --- | --- | --- | --- |
| 4 | 55 | 否 | 55 |
| 3 | 65 | 否 | 65 |
| 2 | 80 | 否 | 80 |
| 1（正灵根） | 95 | 否 | 95 |
| 1（风/雷/冰） | 95 | +10 | 100 |

注意：现有判定是「只要灵根中含风/雷/冰，就标记为变异灵根」，因此风/雷/冰角色在四灵根、三灵根时也会显示变异标签。强度仍按根数上限，不额外叠加。显示层建议写成「变异·四灵根」「变异·单灵根」，避免标签通胀。

### 14.4 生成规则

```text
preferences = [角色元素映射, ...旁支顺序].slice(0, rootCount)
roots = generateSpiritualRoots(aptitudeScore, preferences, rngRoots)
assert roots.some(root => root.element === 角色元素映射)
```

`generateSpiritualRoots` 的现有签名是 `(score, preferences, rng)`，见 [utils.ts](../packages/game-rules/src/character/creation/utils.ts)。

约束：

- 生成后必须断言首元素存在；不存在则整单失败，不降级到随机灵根。
- 资质分按档位固定为 45 / 62 / 78 / 92 / 100，直接传给现有生成器；它会同时影响灵根强度目标与寿元（>80 时寿元 +20）。
- 灵根强度沿用现有公式与随机抖动，不额外给首灵根保底。
- 结果落库后不可重 roll；同一 `journeyId` 重试必须得到同一份灵根。
- 灵根顺序按「首灵根、旁支」固定，不按强度重排，保证角色识别稳定。

### 14.5 灵根与初始战力的关系

必须明确：**灵根强度当前不直接进入战斗面板。** 它目前影响修炼速度与资质/寿元，不直接加气血、攻击、防御。

因此本文的「灵根档 → 初始战力档」不是让灵根直接加战斗属性，而是让灵根档承担三个职责：

1. 决定修炼速度与长期成长；
2. 决定可承载的开局道法数量与品阶（第 16 节）；
3. 决定献祭档位对应的道装与物资（第 17 节）。

这三项共同构成开局的实战差异。若后续希望灵根直接参与战斗，应单独立项做「灵根亲和」规则，不在本期偷偷塞进属性。

### 15.3 开局战力指数（OPI）

OPI 只用于策划校准与验收，定义如下：

```text
OPI = 100 × (
  0.30 × 有效气血 / 基准气血 +
  0.25 × 十回合有效输出 / 基准输出 +
  0.20 × 有效承伤 / 基准承伤 +
  0.15 × 身法先手 / 基准身法 +
  0.10 × 功能覆盖 / 基准功能
)
```

其中：

- 有效气血 = 气血 + 护盾期望；
- 有效承伤 = 气血 /（1 - 综合减伤）；
- 功能覆盖 = 治疗、增益、控制、解控的覆盖率，按回合上限截断；
- 基准值取 T1 全角色平均，基准 OPI = 100；
- OPI 不落库、不进 contracts、不进道装领域，也不作为客户端展示的「战力」。

### 15.4 档位目标与验收带

| 档位 | 基准 OPI | 验收带 |
| --- | --- | --- |
| T1 | 100 | 95-105 |
| T2 | 120 | 114-126 |
| T3 | 145 | 138-152 |
| T4 | 175 | 166-184 |
| T5 | 210 | 199-221 |

设计意图：T5/T1 约 2.1 倍，不出现「一档碾压三档」；高献祭档的主要优势是稳定性、容错与成长速度，而不是开局数值爆炸。

### 15.6 为什么不做战力字段

- 道装领域已有明确约束：不得新增品质/战力字段，计算由属性与内容共同得出；
- 玩家侧显示「战力」会诱发跨系统比较，和现有境界/道装/功法展示重复；
- OPI 依赖模拟对局，不适合作为持久化真值。

对外展示建议：境界、灵根谱、本命道法、道装品阶、已学功法，不显示单一数字。

### 15.7 校准方法

- 用现有 V6 投影拿到真实面板与技能列表；
- 在本地用现有战斗模拟跑十回合对局，记录有效输出、承伤、治疗/护盾覆盖；
- 按档位目标 OPI 调整随机道法预算与道装件数；
- 不新增常驻 benchmark/seed 脚本；临时评估脚本不入库。

## 16. 初始技能设计

### 16.1 三层结构

| 层 | 数量 | 性质 | 来源 |
| --- | --- | --- | --- |
| 本命道法 | 1 | 主动，角色固定 | 逐角色内容 |
| 随机道法 | 0-3 主动 + 1-3 被动 | 主动/被动混合 | 开局道法池 |
| 炼气功法 | 1 本已学 | 被动 | 现有 6 本炼气功法 |

设计目的：

- 本命道法保证角色识别，不是纯随机；
- 随机道法保证每局有差异；
- 炼气功法复用现有系统，不另造一套被动。

### 16.2 随机数量

| 档位 | 本命 | 随机主动 | 随机被动 | 功法 | 功法起始层 |
| --- | --- | --- | --- | --- | --- |
| T1 | 1 | 0 | 1 | 1 本 | 1 |
| T2 | 1 | 1 | 1 | 1 本 | 1 |
| T3 | 1 | 1 | 1 | 1 本 | 2 |
| T4 | 1 | 2 | 2 | 1 本 | 2 |
| T5 | 1 | 2 | 3 | 1 本 | 3 |

约束：

- 同一 ID 不重复；
- 开局道法主动总数不超过 3（本命 + 随机）；
- 道装器诀另计，但「本命 + 随机主动 + 器诀」同一场战斗的主动技能总数不超过 6；
- 被动道法总数不超过 4；
- 开局炼气功法层数不超过 3（低于现有 `maxLevel 9` 的上限，仅限制开局投放）；

### 16.5 品阶与数值缩放

开局道法分五档品阶，对应档位：

| 档位 | 品阶 | 缩放 |
| --- | --- | --- |
| T1 | 凡品 | 0.70 |

缩放只作用于该道法的区间内，不能突破区间上限。例如「破岳式」在 T5 取 170% × 1.30 会超上限，因此规则是**先按品阶取区间内的位置，再取上限截断**，不允许乘出 221%。

### 16.6 元素亲和权重

抽取时按角色首灵根加权：

| 关系 | 权重 |
| --- | --- |
| 本元素 | 3 |
| 生我元素 | 1.5 |
| 其他 | 1 |

五行相生：木生火、火生土、土生金、金生水、水生木。变异元素的「生我」按：冰←水、雷←火、风←木。

本命道法固定为本元素，因此「至少有一个本元素技能」由本命保证，随机池不再做强约束。

### 16.7 本命道法

- 每个角色 1 个，固定主动；
- 名字与效果转译自角色元素战技/爆发，但使用道友战斗原语；
- 本命道法不进入随机池，不能被重 roll；
- 本命道法可以随境界成长，但开局固定 1 级；
- 首批 36 个角色的本命见第 18 节表。

### 16.8 随机与落库

```text
templateId = `gi:${avatarId}`
seed = sha256(`${journeyId}:${templateId}`).readUInt32BE(0)

rngRoots  = deterministicRng(sha256(`${seed}:roots`))
rngSkills = deterministicRng(sha256(`${seed}:skills`))
rngGear   = deterministicRng(sha256(`${seed}:gear`))

本命 = template.signatureArtId
主动 = weightedSample(activePool, countActive, elementWeights, rngSkills)
被动 = weightedSample(passivePool, countPassive, elementWeights, rngSkills)
功法 = weightedSample(manualPool, 1, roleWeights, rngSkills)
```

- 灵根、技能、道装使用独立子种子（`:roots`、`:skills`、`:gear`），避免某一内容池变化导致其他部分漂移；
- 随机结果只在创建时生成一次；
- 结果写入 `wanjiedaoyou_cultivator_innate_arts`，存 artId、kind、source、quality、level、seed；
- 后续展示与战斗投影只读快照，不重新抽取；
- 内容池后续增删不影响既有角色。

### 16.9 与既有系统的关系

| 系统 | 关系 |
| --- | --- |
| 个人功法 | 开局只学 1 本炼气功法；额外功法以玉简入包，不占槽 |
| 宗门功法/神通 | 本命道法不替代宗门神通；两者可并存，按 ID 去重 |
| 道装器诀 | 器诀是主动技能来源之一；若随机到同名 ID，去重并顺延 |
| 器蕴 | 只提供被动/属性，不参与主动抽取 |
| 灵兽技能 | 开局不发放灵兽技能；灵兽后续单独捕捉/培养 |

### 16.10 战斗投影顺序

建议顺序：

```text
基础属性
→ 个人功法被动
→ 开局被动
→ 宗门被动
→ 道装器蕴/阵纹
→ 开局主动 + 本命
→ 宗门主动
→ 道装器诀
```

规则：

- 同名 ID 只生效一次，先到先得；
- 主动技能列表按「本命、开局主动、宗门主动、器诀」排序；
- 不改变现有行动规则、法力消耗、冷却与目标选择；
- 投影诊断新增 `OPENING_ART_UNKNOWN`、`OPENING_ART_REALM_LOCKED`、`OPENING_ART_DUPLICATE`。

### 16.11 降级实现

如果本期不批准新技能子系统，可用降级方案：

- 被动：随机 1-3 本炼气功法（但炼气只有 1 槽，多余只入包），实战被动仍只有 1 本；
- 主动：只靠开局道装的器诀（0-2 条）；
- 本命：暂时做成一本角色专属炼气功法（被动），不提供主动技能。

降级方案能上线，但无法满足「主动/被动随机」的完整体验，只作为风险兜底。

- 装备等级固定器阶 10，不随献祭档提高器阶；
- 器阶 30 需要筑基初期（25 级），不进入开局，原因见第 12 节；
- 阵纹只开现有 9 种中的通用项，优先角色定位对应项；
- 轻灵在器阶 10 下不产生额外收益（最低门槛已是炼气初期），因此不进入开局器蕴池，避免浪费器蕴槽。

### 17.3 器诀抽取

- 从现有 38 条器诀中抽取；
- 优先角色首灵根对应元素，其次通用；
- 同一角色不重复；
- 器诀只装在武器/法兵优先，其次是法衣；
- 器诀是主动技能，计入「本命 + 随机主动 + 器诀 ≤ 6」的战斗主动总数约束。

### 17.5 发放方式

推荐用**一封「转世开局礼」邮件**承载全部物资，避免多封邮件与顺序问题：

- 标题：`转世开局礼`
- 正文：按档位生成一句叙述，说明献祭档位与所赠道装；
- 附件：灵石、丹药、灵果、玉简；
- 道装：在创建事务内直接生成实例并自动穿戴，不放入邮件（避免邮件领取时的随机性）；
- 若自动穿戴失败，则道装入包并记录诊断，不阻断建号。

### 17.6 幂等与审计

- `journey_id` 唯一；重复请求返回同一 `cultivatorId`，不重复发奖；
- 若首次事务失败，账本状态为失败/未完成，允许同 journeyId 重试；
- 记录：档位、种子、灵根、本命、随机技能 ID、道装实例 ID、邮件 ID；
- 管理端可查「某 journeyId 发了什么」，用于客诉与回滚。

### 17.7 绑定与流通

建议开局道装**绑定不可交易**。若现有 `inventory_items` 没有绑定字段：

- 方案 A：新增 `bound` / `source` 字段；
- 方案 B：在交易/拍卖/回收入口按 `source = 'opening'` 拦截；
- 方案 C：本期先不绑定，但限制器阶 10 的售价上限。

优先方案 B，避免为单一活动改表；若已有回收/交易过滤点，直接复用。

## 20. 验收标准

### 20.1 功能

- 5 个档位都能建号成功，且灵根数分别为 4/3/2/1/1；
- 每个角色的灵根谱都包含其原神元素首灵根；
- T5 道装为 6 件，全部器阶 10；
- 炼气初期（5 级）能穿戴全部开局道装；
- 开局只学 1 本炼气功法，额外玉简在包内；
- 开局道法主动不超过 3、被动不超过 4；含器诀的战斗主动总数不超过 6；
- 同一 `journeyId` 重复请求返回同一角色，不重复发奖。

### 20.2 随机与确定性

- 同一 `journeyId` 重建（清理测试数据后）得到相同灵根、技能、道装；
- 不同 `journeyId` 有可见差异；
- 内容池更新后，既有角色的技能快照不变。

### 20.3 安全

- 无内部密钥拒绝；
- `starterTier` 为 0、6、小数、字符串时拒绝；
- `avatarId` 越界拒绝；
- `combatPower` 不改变六维总和、技能数量、道装数量；
- 文本过滤命中时拒绝建号。

### 20.4 经济

- 开局礼只有一封，灵石为档位总额，不再叠加 20,000；
- 开局道装不可通过拍卖/交易/回收套利（按 17.7 方案）；
- T5 总物资价值有上限，不随 `combatPower` 增长。

### 20.5 战斗

- 本命、随机主动、器诀都能在战斗中出现且不重复；
- 被动合并后六维/减伤/暴击等数值在预算内；
- 不出现未解锁境界技能；
- 十回合模拟不出现无限循环、负治疗、护盾溢出。

### 20.6 命令

pnpm run test
pnpm run build

## 21. 风险与待确认

| 风险/问题 | 影响 | 建议 |
| --- | --- | --- |
| 新技能子系统成本高 | 需改投影、内容、数据库 | 先做降级方案或分批上线 |
| 36 个本命道法内容量大 | 文案与数值容易失配 | 首批 8 个，剩余按元素/定位批量 |
| T4/T5 灵根档相同 | 玩家可能认为 T5 没提升 | 用「满献祭」与技能/道装解释；或另立「天灵根·圆满」+5 上限 |
| `combatPower` 量纲未知 | 阈值不可靠 | 默认不参与；阈值配置化后再启用 |
| 金灵根没有原神对应 | 角色识别弱 | 金只作旁支，首灵根永远是角色元素 |
| 开局道装绑定字段不存在 | 可能被交易套利 | 用 source 过滤交易入口，避免改表 |
| 炼气只有 1 个功法槽 | 多本功法无法立即生效 | 只装 1 本，其余给玉简 |
| 灵根强度不进战斗 | 档位差异被质疑 | 明确由技能/道装承担；灵根亲和另立项 |
| 宗门映射仍用旧方案 | 旧文档与新五档可能冲突 | 以旧文档的 starterTier→宗门表为准，本文不改 |
| 献祭档可能为 0 或 6 | 越界 | 严格拒绝，不 clamp |

### 待确认

1. 「初始战斗力」是否接受 OPI 作为验收指标，而不是玩家可见战力？
2. 是否批准新增「开局道法」子系统，还是先走降级方案？
3. T5 是否允许比 T4 多 5 点灵根强度上限（新增规则），还是保持同档？
4. 开局道装是否绑定？若绑定，用字段还是交易入口过滤？
5. `combatPower` 是否启用「底蕴分位」？若启用，阈值由谁提供？
6. 首批 8 个角色是否按 18.3 的建议？

## 附录 B：随机伪代码

```ts
function buildOpeningBuild(input: {
  journeyId: string;
  template: CharacterTemplate;
  tier: 1 | 2 | 3 | 4 | 5;
}) {
  const counts = OPENING_COUNTS[input.tier];
  const seed = hashSeed(`${input.journeyId}:${input.template.id}`);

  const rngRoots = deterministicRng(hashSeed(`${seed}:roots`));
  const rngSkills = deterministicRng(hashSeed(`${seed}:skills`));
  const rngGear = deterministicRng(hashSeed(`${seed}:gear`));

  const roots = buildRoots(
    input.template.rootLine,
    counts.rootCount,
    rngRoots,
  );

  const active = weightedSample(
    ACTIVE_POOL,
    counts.active,
    elementWeights(input.template.element),
    rngSkills,
  );
  const passive = weightedSample(
    PASSIVE_POOL,
    counts.passive,
    elementWeights(input.template.element),
    rngSkills,
  );
  const manual = pickManual(input.template, rngSkills);

  return {
    roots,
    signatureArtId: input.template.signatureArtId,
    active,
    passive,
    manual,
    equipment: buildStarterEquipment(input.tier, input.template, rngGear),
    supplies: STARTER_SUPPLIES[input.tier],
  };
}
```
