## 第一部分 · 寿元体系

> 原文档版本：v8（2026-11-09）
> 原变更记录：v2 补充人界纪年与自然衰老；v3 补充历练/闭关按年对照与统一时钟方案；v5 新增战败折寿；v6 删除战斗死亡与保命符；v7 与当前代码对齐并覆盖到渡劫；v8 突破改为境界基础寿命。v4 的寿元减半口径已在 v7 撤销。

## 1. 项目背景

当前寿元系统存在三套并行语义：

- **自然衰老**：人界纪年按现实时间推进（现实 12 小时 = 游戏 1 年），生产环境 cron 持续增加活跃角色 `age`；
- **闭关**：玩家主动推进 `age`，一次 1～200 年；
- **副本选项**：直接扣 `lifespan`（寿元上限）。

三者最终都以 `age >= lifespan` 判定死亡，但玩家只看到一个 `age / lifespan` 比值，无法判断某次操作消耗的是"已活岁月"还是"剩余寿命"，也无法得知即使不操作角色也会随现实时间老去。

同时，各境界纯闭关修为覆盖率仅 10%～19%，寿元实际上没有参与成长决策，只是死亡倒计时。大境界突破把寿元抬到境界基础寿命（炼气 100 → 渡劫 8000），与经验需求 1.7～5.3 倍的增长节奏缺少共同推导依据。

本项目的目标不是简单调高或调低寿元，而是先统一语义，再决定寿元在玩法中的定位。

### 2.3 寿元来源

**初始生成**

- 年龄：`14 + random(0～5)`，即 14～19 岁。
- 寿元：`80 + random(0～19)`；资质分 > 80 再 +20。
- 结果区间：80～99；高资质 100～119。

代码：`packages/game-rules/src/character/creation/CharacterGenerator.ts`；转世建号 `externalJourney.ts` 使用同一寿元口径，年龄为 14～17 岁。

**大境界突破：切换境界基础寿命**

只有跨大境界才改变寿元，阶段内突破不影响。突破时不再把固定值累加到当前寿元，而是把寿元抬到目标境界的基础寿命：

`lifespan = max(当前 lifespan, 目标境界基础寿命)`

这样延寿丹、灵果、宗门恩赏带来的额外寿元不会被覆盖，也不会因反复突破重复叠加基础值。

| 金丹 | 500 | +300 |
| 元婴 | 1200 | +700 |
| 化神 | 2000 | +800 |
| 炼虚 | 3000 | +1000 |
| 合体 | 4000 | +1000 |

| 筑基 | 25～40 | 200 | +100 | 181～186 |
| 金丹 | 45～60 | 500 | +300 | 481～486 |
| 元婴 | 65～80 | 1200 | +700 | 1181～1186 |
| 化神 | 85～100 | 2000 | +800 | 1981～1986 |
| 炼虚 | 105～120 | 3000 | +1000 | 2981～2986 |

### 2.5 人界纪年法与自然衰老

人界纪年不是展示用的日期，而是寿元系统的被动时钟。

| 项目 | 规则 | 代码 |
| --- | --- | --- |
| 纪年起点 | 2026-10-18 00:00（UTC+8） | `GAME_CALENDAR_EPOCH_MS` |
| 现实→游戏月 | 现实 60 分钟 = 游戏 1 月 | `REAL_MS_PER_GAME_MONTH` |
| 现实→游戏年 | 现实 12 小时 = 游戏 1 年 | `REAL_MS_PER_GAME_YEAR` |
| 历法结构 | 30 日/月、12 月/年 | `calendar.ts` |
| 自然衰老 | 每满 1 游戏年，`age += 1`，锚点前移并保留不足一年的零头 | `advanceNaturalAging` |
| 调度 | 生产环境每 10 分钟扫描一次；只处理 `aging_synced_at` 早于「当前时间 − 1 游戏年」的 active 角色 | `BACKGROUND_SCHEDULES`、`runWorldAgingTickJob` |
| 死亡 | 结算后 `age >= lifespan` 直接 `status = 'dead'`、写 `died_at`，不生成寿元故事 | `internalCron.ts` |
| 展示 | 顶部 HUD 显示「人界X年X月X日」 | `useGameHudModel`、`GameTopHud` |

因此寿元同时具有两种时间尺度：

- **游戏内尺度**：100/200/500/1200/2000/3000/4000/5000/8000 年，用于闭关与修为预算；
- **现实尺度**：1 游戏年 = 12 小时，寿元就是账号级倒计时。

| 筑基 | 181～186 年 | 90.5～93 天 | 约 3.0～3.1 个月 |
| 金丹 | 481～486 年 | 240.5～243 天 | 约 8.0～8.1 个月 |
| 元婴 | 1181～1186 年 | 590.5～593 天 | 约 1.6 年 |
| 化神 | 1981～1986 年 | 990.5～993 天 | 约 2.7 年 |
| 炼虚 | 2981～2986 年 | 1490.5～1493 天 | 约 4.1 年 |
| 合体 | 3981～3986 年 | 1990.5～1993 天 | 约 5.5 年 |
| 大乘 | 4981～4986 年 | 2490.5～2493 天 | 约 6.8 年 |

## 3. 寿元消耗途径

### 3.1 自然衰老：现实时间推进年龄

- 入口：`runWorldAgingTickJob`（`apps/api/src/runtime/jobs/internalCron.ts`）
- 规则：`advanceNaturalAging`（`packages/game-rules/src/world/aging.ts`）；每满 1 游戏年 `age += 1`，锚点向前移动一年并保留不足一年的零头
- 时钟：`GAME_CALENDAR_EPOCH_MS` 起算，现实 12 小时 = 1 游戏年
- 调度：生产环境每 10 分钟扫描一次（`*/10 * * * *`），只处理 `aging_synced_at` 落后超过 1 游戏年的 active 角色
- 死亡：`age >= lifespan` 时直接 `status = 'dead'` 并写 `died_at`，不走 `handleLifespan`、不生成寿元耗尽故事
- 环境差异：`CronService` 只在 `NODE_ENV === 'production'` 启动；本地/dev 只能手动调用 `/internal/cron/world-aging-tick`

作用：不依赖玩家操作、持续消耗同一条寿命的被动时钟。它把寿元从"修炼预算"变成了"账号存活时间"，也是炼气角色约 41 天后自然老死的直接原因。

### 3.2 闭关：推进年龄

- 入口：`apps/api/src/cultivator/application/RetreatApplicationService.ts`
- 规则：`packages/game-rules/src/cultivation/CultivationEngine.ts`，`performCultivation` 中 `age += years`
- 年限：单次 1～200 年
- 前置校验：`lifespan - age >= years`，否则拒绝
- 灵气成本：`ceil(years / 10) × 4`；灵气上限 240，自然恢复 1 点/6 分钟
- 死亡：`age >= lifespan` 时置 `dead`，生成寿元耗尽故事
- 突破：`attemptBreakthrough` 不增加年龄，历史记录 `years_spent: 0`

作用：玩家主动推进年龄的路径，可与自然衰老叠加；同时是修为来源之一，但效率远不足以覆盖阶段需求。

### 3.3 副本选项：削减寿元上限

- 入口：`apps/api/src/dungeon/application/flow/DungeonFlowService.ts`
- 选项成本由 LLM 生成，`costs` 可包含 `lifespan`
- 服务端硬上限：`DUNGEON_LIFESPAN_COST_MAX = 120`
- 公式：`境界基础值 × 难度倍率 × 档位倍率`，最小 1

| 境界 | 境界基础寿命 | 基础值 | 单次成本区间 | 五轮全高成本 | 占基础寿命 |
| --- | --- | --- | --- | --- | --- |
| 炼气 | 100 | 1 | 1～3 | ≈15 | ≈15.0% |
| 筑基 | 200 | 2 | 1～6 | ≈30 | ≈15.0% |
| 金丹 | 500 | 3 | 1～9 | ≈45 | ≈9.0% |
| 元婴 | 1200 | 5 | 2～16 | ≈80 | ≈6.7% |
| 化神 | 2000 | 8 | 3～25 | ≈125 | ≈6.3% |
| 炼虚 | 3000 | 12 | 5～38 | ≈190 | ≈6.3% |
| 合体 | 4000 | 18 | 7～57 | ≈285 | ≈7.1% |
| 大乘 | 5000 | 25 | 9～79 | ≈395 | ≈7.9% |
| 渡劫 | 8000 | 35 | 13～110 | ≈550 | ≈6.9% |

> 单次成本区间 = 基础值 × 难度倍率（0.75～1.8）× 档位倍率（0.5～1.75），并受 `DUNGEON_LIFESPAN_COST_MAX = 120` 截断；占基础寿命按 2.4 的 100/200/500/1200/2000/3000/4000/5000/8000 计算。

执行链：`applyDungeonCosts` → `ResourceEngine` → `updateLifespan(-value)`；若 `age >= lifespan` 且角色仍 active，直接置 `dead`。

作用：唯一直接削减寿元上限的常规玩法；境界越高，相对损失反而越小。

### 3.4 战斗不判死：败方只折寿

现状代码的战斗结算不涉及死亡与寿元：气血归零只结束战斗，不写 `dead`，仓库中也不存在 `resolveBattleDeath` / `death_save`。v6 目标是把战败转换为 3.7 的折寿，仍然不判死。

| 结局 | 概率（同阶） | 折寿倍率 |
| --- | --- | --- |
| 重伤撤退 | 67% | ×1 |
| 濒死 | 33% | ×2 |

- 每差 1 个境界阶位：濒死概率 +10%，上限 100%；不再计算死亡概率。
- 战斗结算只写状态与 `lifespan`，不写 `dead`；不需要保留或新增保命符。
- 角色死亡只来自寿元耗尽（自然衰老、闭关、副本折寿），以及主动兵解/转世；战败不会直接判死。

作用：战斗从"平行死亡线"降级为寿元消耗渠道，死亡入口收敛为唯一一条。

### 3.5 主动兵解与转世

- `reincarnateActiveCultivator`：主动结束当前角色，`status = 'dead'`
- 死亡后新建角色走初始生成流程，不继承寿元、修为或加成
- `getLastDeadCultivatorSummary` 只提供前世摘要

### 3.6 灵兽寿命（对照体系）

- 固定上限 1000
- 战死扣 50
- 出战最低寿命 50
- 休养每灵石恢复 10

与人物寿元的区别：灵兽有恢复手段、固定上限、按次扣减；人物寿元只能靠突破/丹药增长，按年消耗。同名字段规则不同，容易在策划与 UI 上产生歧义。

### 3.7 战败折寿（v5 新增核心机制）

**定位**：战败不再判死，而是直接削减这一世的寿元上限。每一次战败都变成不可逆的时间损失，把战斗结果接入同一本寿元账，是方案 B/D「寿元即时间货币」的核心支撑。

**规则**

- 触发：战斗终局判负（气血归零）的败方；胜负与折寿值全部由服务端计算，客户端不能上报。
- 折寿对象：败方的 `lifespan` 上限，不扣 `age`；`remaining = lifespan - age` 同步减少。
- 计算公式：`折寿 = 境界基准值 × 结果倍率 × 战斗类型倍率`。

| 境界 | 境界基础寿命 | 基准折寿 | 占基础寿命 | 折合现实 |
| --- | --- | --- | --- | --- |
| 炼气 | 100 | 4 | 4.0% | 2 天 |
| 筑基 | 200 | 7 | 3.5% | 3.5 天 |
| 金丹 | 500 | 18 | 3.6% | 9 天 |
| 元婴 | 1200 | 42 | 3.5% | 21 天 |
| 化神 | 2000 | 70 | 3.5% | 35 天 |
| 炼虚 | 3000 | 105 | 3.5% | 52.5 天 |
| 合体 | 4000 | 140 | 3.5% | 70 天 |
| 大乘 | 5000 | 175 | 3.5% | 87.5 天 |
| 渡劫 | 8000 | 280 | 3.5% | 140 天 |

| 结局 | 结果倍率 | 炼气 / 筑基 / 金丹 / 元婴 / 化神 / 炼虚 / 合体 / 大乘 / 渡劫 |
| --- | --- | --- |
| 重伤撤退 | ×1.0 | 4 / 7 / 18 / 42 / 70 / 105 / 140 / 175 / 280 |
| 濒死 | ×2.0 | 8 / 14 / 36 / 84 / 140 / 210 / 280 / 350 / 560 |

| 战斗类型 | 类型倍率 |
| --- | --- |
| 切磋 / 友谊赛 | ×0（不折寿） |
| PVE 常规 | ×1.0 |
| 副本首领 / 秘境 | ×1.5 |
| PVP 常规 | ×0.5 |

- 不判死：战斗结算不写 `dead`，`death_save` 保命符下线；气血归零只决定重伤/濒死与折寿档位。
- 下限保护：折寿后 `lifespan` 不低于 `age + 1`；触底不再扣，改为施加「寿元将尽」状态（方案 B/D），折寿本身不写 `dead`。
- 不可自然恢复：折掉的寿元只能靠大境界突破、延寿丹/灵果、宗门恩赏补回。
- 防滥用：
  - 单次折寿硬上限 200 年；
  - 单日累计不超过当前 `lifespan` 的 10%；
  - 同一角色当日第 4 次及以后战败，折寿减半；
  - PVP 被同一对手重复击败，第 2 次起折寿减半；
  - 组队/宗门战按个人败方结算，不连坐队友。
- 幂等：以 `battleId + 败方 cultivatorId` 为唯一键，战局重放或消息重投不重复扣。
- 与副本折寿叠加：副本内战败可同时触发副本选项折寿与战败折寿，但当日累计仍受 10% 上限约束，结算页分项展示。

**实现落点**

| 层 | 位置 | 改动 |
| --- | --- | --- |
| 规则 | `packages/game-rules/src/combat/` | 新增 `calculateDefeatLifespanLoss` 纯函数（基准表 + 倍率 + 下限 + 日上限） |
| 内容 | `packages/game-content/src/combat/` | 战败折寿基准值与倍率配置 |
| 服务 | `apps/api/src/combat/application/` 战斗终局结算 | 败方写入 `lifespan`、幂等、写来源日志，统一走死亡结算器 |
| 数据 | `cultivators.lifespan` | 复用，无新列；折寿记录进日志/事件，来源 `battle_defeat` |
| 前端 | 战斗结算页 | 显示「战败折寿 X 年 / 剩余 Y 年」 |

**验收**

- 纯规则单测：基准值、结果/类型倍率、`age + 1` 下限、单日 10% 上限、幂等键。
- 实机：同阶战斗战败一次，结算页与角色面板的 `lifespan` 同步减少；气血归零后角色状态仍为存活；触底只进入寿元将尽，不判死；同一 `battleId` 重投不重复扣。

**与现状的关系**：现状战斗不判死也不折寿；v6 目标为「战败按 3.7 折寿、仍不判死」，实施时只需新增折寿结算，不需要下线任何战斗死亡逻辑。

1. 历练按现实时间产出、不耗寿元；自然衰老按现实时间扣年、不产修为。二者同频，年龄只决定"能领多少次历练"，不决定单次收益。
2. 闭关是"用未来换现在"：每闭关 1 年，少活 0.5 天，损失约 9.6% 日预算的历练收入，只换回 0.58% 日预算。除寿元本会溢出、需要短期爆发外，闭关是负期望。
3. 突破不耗时、副本只折上限、灵兽寿命可恢复，都会进一步削弱"年"作为成本的地位。
4. 感悟的瓶颈在历练而非寿元：完美突破需 50 感悟，闭关约需 714 年，历练约 2.8 年（现实 1.4 天）。
5. 与第 5 节 P1-11 一致：寿元没有参与成长决策。若要让它参与，必须先统一时间口径（见方案 D）。

## 5. 问题清单

### P0 · 规则与语义

1. **三套消耗语义**：自然衰老推 `age`、闭关推 `age`、副本扣 `lifespan`，三条路径都能触发 `dead`，但 UI 只有一个比值，玩家无法区分"自然老去/闭关预支/折寿"。
2. **自然衰老死亡静默**：`runWorldAgingTickJob` 直接置 `dead`，未调用 `handleLifespan`，未见寿元耗尽故事与死亡事件投递，只做 `invalidateActiveCultivatorRef` 缓存失效。玩家可能在上线时才发现角色已老死。
3. **突破不耗时**：规则层突破不增加年龄，历史记录 `years_spent: 0`；服务层剧情文案却传 `yearsSpent: 1`。叙事与规则不一致。
4. **函数语义不一致**：`consumeLifespanAndHandleDepletion` 名为"消耗寿元"，闭关调用时传入 `ageAfterConsumption`，实际只做死亡判定，不写寿元。
5. **闭关校验使用陈旧年龄**：校验 `lifespan - age >= years` 读取的是数据库快照，不做按锚点的即时推导；cron 结算前存在约 10 分钟的跨年窗口，可能出现"校验通过、随即被 cron 判死"。
6. **自然衰老不可本地复现**：`CronService.start()` 只在 `NODE_ENV === 'production'` 启动，dev/local 只能手动调用内部接口，测试与联调容易漏掉该时钟。

### P0 · 时间口径（v3 新增）

7. **时间单位三套并存**：历练用现实小时（上限 24h）、闭关用游戏年、副本用轮次、突破不耗时；同一界面同时出现"小时/年/轮"，玩家无法建立统一时间感。
8. **两个现实时间锚点**：`aging_synced_at` 与 `last_yield_at` 各自从现实时间推导，语义重叠但不共享；衰老、历练、挂机对"过去了多久"的答案互相对不上。
9. **闭关跳年与世界纪年永久错位**：闭关 200 年后角色年龄 +200，而 HUD 纪年只按现实推进；角色经历的时间与世界时间永久分离，且没有任何字段记录这段偏移。

### P1 · 数值

10. **现实时间未进入数值设计**：所有寿元/经验/丹药仍按游戏年设计，但实际时钟是现实 12 小时 = 1 年，没有任何设计文档或公式显式处理"现实时间成本"。
11. **寿元不参与成长决策**：各境界纯闭关覆盖率仅 10%～19%，渡劫最高也不到 20%，寿元仍不是"能否修上去"的约束。
12. **曲线不匹配**：经验需求在金丹后按约 1.7～2.7 倍增长（炼气→筑基约 4 倍），寿元按境界基础寿命 100/200/500/1200/2000/3000/4000/5000/8000 抬升，没有共同推导依据。
13. **丹药量级脱节**：凡品延寿 +10 年（现实 5 天），渡劫基础寿命 8000 年（现实 4000 天）；延寿丹只在低境界有体感。
14. **经验表与目标天数已对齐**：金丹阶段经验表合计 67,000，目标天数口径 `21 × 3,200 = 67,200`，偏差约 0.3%；其余境界偏差均在 1% 以内。
15. **安全上限形同虚设**：单次寿元变动上限 100,000、绝对值上限 10,000,000，正常玩法几乎触碰不到。

### P1 · 系统一致性

16. **死亡入口体验不一致**：自然老死（cron，静默）、闭关寿尽（`handleLifespan`，有故事）、副本寿尽（`ResourceEngine` 直接 `dead`）。战斗不判死，不再进入该清单。
17. **灵兽寿命规则不同**：灵兽可恢复、固定上限、按次扣减；人物不可恢复、按年消耗，同名字段易混淆。
18. **境界与内容已对齐**：`REALM_VALUES`、增寿表、副本寿元成本、经验表与破境演出均覆盖炼气～渡劫；若本轮不开放高境界，需要在入口显式封顶，不能依赖内容缺省。

## 6. 重构方案对比

### 方案 A：寿元货币化（大改）

把"剩余寿元"变成通用资源，所有耗时行为（闭关、副本、探索、赶路、炼丹、突破准备）按年计价；寿元可交易、可抵押，死亡后进入轮回结算。

- 优点：寿元真正进入玩法决策，时间成为核心经济。
- 缺点：改动面最大，涉及所有玩法入口、经济系统、LLM 副本提示词、UI 与存档口径。
- 适用：愿意围绕"时间"重做一轮核心循环。

### 方案 B：软上限 + 叙事时钟（中改，推荐）

保留 `age` / `lifespan` 双字段，但明确规定：

- 自然衰老是唯一被动时钟，按人界纪年推进年龄；
- 闭关是主动预支，推进年龄；
- 副本、重伤、突破失败扣寿元上限，统一走"折寿"结算与文案；
- 寿元低于阈值进入虚弱状态，而不是直接死亡；
- 所有死亡入口统一经过同一个结算器，保证故事、日志与通知一致。

- 优点：改动集中在寿元规则层与少量 UI，存量存档天然兼容，风险可控。
- 缺点：仍保留两个字段，需要靠统一入口避免再次分裂。
- 适用：希望让寿元"有存在感"但不想重做全经济。

### 方案 C：纯叙事时钟（轻改）

寿元只作为境界突破的时间门槛与死亡倒计时，不参与任何玩法成本；副本不再生成寿元成本，寿元丹仅用于延长角色寿命。自然衰老保留为唯一的被动消耗，闭关改为不推进年龄，只消耗灵气与时间窗口。

- 优点：最小改动，清除 LLM 生成寿元成本的不确定性，并消除"现实时钟 + 闭关预支"的双重扣减。
- 缺点：寿元仍不具备策略深度，只是背景设定；闭关不再有"燃烧寿命换修为"的取舍。
- 适用：当前优先级是稳定与内容填充，而不是系统深化。

### 方案 D：统一人界纪年时钟（v3 新增，角色私有时钟）

把"年/月/日"作为唯一时间单位，现实小时只保留为底层调度，不出现在玩法公式与玩家文案中。

- **时钟归属**：每个角色拥有私有纪年，`角色纪年 = 诞辰纪年 + age + 年内余量`；不闭关时与世界纪年同步，闭关即时跳年，角色纪年领先世界纪年。
- **单位换算**：现实 12 小时 = 1 游戏年、1 小时 = 1 游戏月、2 分钟 = 1 游戏日。
- **历练**：由"每现实小时 0.008 日预算、上限 24 小时"改为"每游戏月 0.008 日预算、上限 24 月（2 年）"，公式数值等价；领取门槛改为满 1 年。
- **挂机/讨伐**：6 小时 → 6 月（0.5 年）。
- **市场刷新**：2 小时 → 2 月。
- **灵气恢复**：6 分钟 → 3 日。
- **突破**：固定耗时 1 年，与现有剧情文案 `yearsSpent: 1` 对齐。
- **世界侧系统**（宗门、市场、竞技、活动）继续使用全局世界纪年，不受角色跳年影响。

- 优点：所有玩法共享一套时间语言；闭关、衰老、历练从同一锚点推导，可合并 `aging_synced_at` 与 `last_yield_at` 的语义；修为数值零改动，风险集中在展示层与一次迁移。
- 缺点：同屏玩家角色纪年可能不同，需要在 UI 上明确区分"此身纪年"与"世界纪年"；历练领取间隔从 1 小时拉长到 12 小时，影响日活手感。
- 适用：确定保留即时闭关、又不希望出现小时/年/轮三套口径。

## 7. 推荐方案 B / D 的规则与数值框架

### 7.1 规则定义

- `age`：角色已经活过的年数，由自然衰老（现实 12 小时 = 1 游戏年）与闭关年数共同推进。
- `lifespan`：这一世寿元上限。大境界突破时抬到目标境界的基础寿命（`max(当前, 基础)`），延寿丹药/灵果、宗门恩赏在此基础上叠加。
- `remaining = lifespan - age`：UI 与提示统一使用"剩余寿元"，并换算为现实可存活天数展示。
- 折寿：副本、战败、重伤、突破失败等直接减少 `lifespan`，并在玩家日志中记录来源；战败折寿见 3.7。
- 死亡：唯一入口是寿元耗尽——`remaining <= 0` 时先进入"寿元将尽"状态，仍可救治；再次归零才判死。战斗不再判死。
- 自然衰老统一入口：cron、闭关、副本三条路径都调用同一结算器，统一故事、事件与通知。

### 7.5 统一人界纪年的时间口径（方案 D）

已定决策：

1. 纪年归属：**角色私有时钟**。闭关即时推进角色纪年，HUD 显示"此身纪年"，世界纪年单独展示或作为环境信息。
2. 历练节奏：**每满 1 年可领取一次，单次上限 2 年**。

规则：

- `角色纪年 = 诞辰纪年 + age + 年内余量`；`诞辰纪年 = 当前世界纪年 − age`（存量回填口径，之后闭关才产生偏移）。
- 年内余量由 `aging_synced_at` 推导，保留不足一年的零头，月/日由此换算。
- 所有玩家可见的时间文案只使用"年/月/日"，不再出现"小时""轮""现实天数"；运维日志、邮件保留期等非玩法语义可继续用现实时间。
- 历练、衰老、挂机共用同一"角色时间锚点"，不再各自从 `last_yield_at`、`aging_synced_at` 独立推导。
- 副本、战斗仍可按"轮"结算，但对外展示与成本统一折算为年/月/日。

单位换算：

| 单位 | 现实时长 | 用途 |
| --- | --- | --- |
| 1 游戏年 | 12 小时 | 历练、闭关、寿元、突破 |
| 1 游戏月 | 1 小时 | 历练收益按整月累积（满 1 年可领）、市场刷新 |
| 1 游戏日 | 2 分钟 | 灵气恢复、短耗时行为 |

副作用（需一并写入验收）：

- 历练领取间隔由 1 小时变为 12 小时，日活手感下降；若不愿改手感，可把门槛保留为"满 1 月可领"。
- 突破开始消耗 1 年，炼气可用寿元减少约 1 年。

### 7.6 闭关收益重定价（v3 新增，建议与方案 D 同期）

4.2 节测算显示：同按 1 游戏年折算，历练产出约为闭关的 16.7 倍。统一时间单位（方案 D）只改口径、不改数值，差距原样保留，因此需要单独重定闭关的年收益。

旋钮：`RETREAT_EXP_BUDGET.dailyFractionPerYear`（现 0.005）。200 年批次含倍率后实际系数约 ×1.151（年限 1.1835 × 随机 0.95 × 顿悟期望 1.025）。

四档方案：

| 方案 | 系数 | 闭关/年（含倍率） | 历练:闭关 | 炼气一生覆盖 | 化神一生覆盖 | 一次 200 年等效历练 |
| --- | --- | --- | --- | --- | --- | --- |
| 现状 | 0.005 | 0.58% | 16.7:1 | 15% | 16% | ≈ 6 天 |
| ×4 | 0.02 | 2.30% | 4.2:1 | 61% | 65% | ≈ 24 天 |
| **×6（推荐）** | **0.03** | **3.45%** | **2.8:1** | **91%** | **97%** | **≈ 36 天** |
| ×10 | 0.05 | 5.76% | 1.7:1 | 152% | 162% | ≈ 60 天 |

> 表中「一生覆盖」按 2.5 的剩余寿元（炼气 ≈82 年、化神 ≈1982 年）计算，其余境界同口径外推。

推荐 ×6（0.03）：

1. 单次 200 年闭关从约 6 天历练量提升到约 36 天，闭关首次具备"燃烧寿命换爆发进度"的决策价值。
2. 炼气一生闭关覆盖率由 15% 提到 91%，低境界寿元仍是硬约束；高境界在 B1 压缩曲线（化神 800 年）下覆盖约 38%，不到一次完整需求，寿元稀缺性得以保留。
3. 不追平历练（约 1/2.8），等待流仍可走历练，两条路线并存。
4. 拉满灵根/养元丹/宗门功法（约 ×3）后极限闭关约 10.4%/年，略高于历练 9.6%，高投入角色获得"闭关更优"的正反馈。
5. 瓶颈期减半后 1.73%/年，仍显著低于历练，保留"70% 后转历练/突破"的引导。

连带事项：

- 灵气成本（200 年 = 80 灵气）在收益 ×6 后偏低，暂不联动；如数据过热再改为 `ceil(years/5) × 4`。
- 若寿元维持境界基础寿命（化神 2000 年），×6 下化神一生覆盖约 97%，寿元不再是约束；与 B1 曲线（化神 800 年）打包后回落到约 38%。
- 改动文件：`packages/game-content/src/cultivation/cultivationExpGain.ts`，同步更新该常量上方注释；仅调常量，不改公式与倍率。

- 若采用 B1 曲线，存量高境界角色的 `lifespan` 可能高于新曲线，需要归档口径或按旧值保留，不可直接回写。

- 副本寿元成本由 LLM 生成，提示词与后端上限必须同时调整，否则会出现"文案说折寿 10 年、实际扣 1 年"的错位。

## 9. 待决策问题

> v3 已定：1）纪年采用角色私有时钟；2）历练每满 1 年可领、单次上限 2 年。其余项仍待决策。

1. 寿元定位为"死亡倒计时"还是"时间货币"？决定选 A/B/C/D。
2. 自然衰老是否保留？若保留，现实 12 小时 = 1 游戏年是否合适？炼气角色约 41 天自然老死，会直接影响留存。

4. 自然老死是否需要死亡故事、邮件/站内通知与前世记录？当前为静默判死。
5. 是否向玩家直接展示"现实可存活天数"？这会把寿元从氛围设定变成硬性倒计时。
6. 境界上限已经配置到渡劫；本轮是否全部开放，还是先在入口显式封顶到化神？若封顶，应限制入口，而不是隐藏已存在的内容。
7. 突破失败是否折寿？需要和成功率、丹药供给一起评估。
8. 转世是否保留前世加成？当前无继承。
9. 延寿丹是否加入耐药或单世上限？决定寿元经济能否长期收敛。
10. 灵兽寿命是否与人物寿元统一命名与规则？
11. 闭关年收益系数取哪一档（7.6：×4 / ×6 推荐 / ×10）？是否与 B1 压缩寿元曲线同期上线？
12. 战败折寿对全部 PVE 生效，还是只对副本/秘境首领生效？常规切磋必须保持 ×0。
13. PVP 是否默认开启折寿？开启前需要匹配保护，否则新手可能被连续击败直接打空寿元。
14. 折寿触底只进入「寿元将尽」可救治窗口，不判死（已定，见 3.7）。

## 14. 灵根设计

### 14.1 原神元素到灵根的映射

原神只有七元素，道友有金木水火土风雷冰八灵根。映射如下：

| 原神元素 | 首灵根 | 说明 |
| --- | --- | --- |
| 火 Pyro | 火 | 正灵根 |
| 水 Hydro | 水 | 正灵根 |
| 冰 Cryo | 冰 | 变异灵根 |
| 雷 Electro | 雷 | 变异灵根 |
| 风 Anemo | 风 | 变异灵根 |
| 土 Geo | 土 | 正灵根 |
| 木 Dendro | 木 | 正灵根 |
| 无对应 | 金 | 只作为旁支灵根，不设「金系原神角色」 |

**首灵根永远是角色自身元素。** 金灵根只通过旁支出现，用来体现剑修、器修与「金主杀伐」的世界观，不允许覆盖角色的原神元素。

### 14.2 旁支灵根顺序

为了让 36 个角色可批量配置、又有稳定的五档结构，旁支按元素统一给定，后续可按角色微调：

| 元素 | 第 1 灵根（首） | 第 2 灵根 | 第 3 灵根 | 第 4 灵根 |
| --- | --- | --- | --- | --- |
| 火 | 火 | 金 | 木 | 土 |
| 水 | 水 | 木 | 金 | 土 |
| 冰 | 冰 | 水 | 金 | 木 |
| 雷 | 雷 | 金 | 火 | 土 |
| 风 | 风 | 木 | 水 | 金 |
| 土 | 土 | 金 | 火 | 水 |
| 木 | 木 | 水 | 土 | 金 |

生成时按档位截取：

- T1：取全部 4 个；
- T2：取前 3 个；
- T3：取前 2 个；
- T4 / T5：只取首灵根。

这样每个角色的灵根谱都是确定的，随机只发生在灵根强度与技能上。

### 14.3 灵根强度与标签

直接复用现有生成器，不新增根数上限：

| 根数 | 基础上限 | 变异加成 | 最终上限 |
| --- | --- | --- | --- |
| 4 | 55 | 否 | 55 |
| 3 | 65 | 否 | 65 |
| 2 | 80 | 否 | 80 |
| 1（正灵根） | 95 | 否 | 95 |
| 1（风/雷/冰） | 95 | +10 | 100 |

注意：现有判定是「只要灵根中含风/雷/冰，就标记为变异灵根」，因此风/雷/冰角色在四灵根、三灵根时也会显示变异标签。强度仍按根数上限，不额外叠加。显示层建议写成「变异·四灵根」「变异·单灵根」，避免标签通胀。

### 14.4 生成规则

```text
preferences = [角色元素映射, ...旁支顺序].slice(0, rootCount)
roots = generateSpiritualRoots(aptitudeScore, preferences, rngRoots)
assert roots.some(root => root.element === 角色元素映射)
```

`generateSpiritualRoots` 的现有签名是 `(score, preferences, rng)`，见 [utils.ts](../packages/game-rules/src/character/creation/utils.ts)。

约束：

- 生成后必须断言首元素存在；不存在则整单失败，不降级到随机灵根。
- 资质分按档位固定为 45 / 62 / 78 / 92 / 100，直接传给现有生成器；它会同时影响灵根强度目标与寿元（>80 时寿元 +20）。
- 灵根强度沿用现有公式与随机抖动，不额外给首灵根保底。
- 结果落库后不可重 roll；同一 `journeyId` 重试必须得到同一份灵根。
- 灵根顺序按「首灵根、旁支」固定，不按强度重排，保证角色识别稳定。

### 14.5 灵根与初始战力的关系

必须明确：**灵根强度当前不直接进入战斗面板。** 它目前影响修炼速度与资质/寿元，不直接加气血、攻击、防御。

因此本文的「灵根档 → 初始战力档」不是让灵根直接加战斗属性，而是让灵根档承担三个职责：

1. 决定修炼速度与长期成长；
2. 决定可承载的开局道法数量与品阶（第 16 节）；
3. 决定献祭档位对应的道装与物资（第 17 节）。

这三项共同构成开局的实战差异。若后续希望灵根直接参与战斗，应单独立项做「灵根亲和」规则，不在本期偷偷塞进属性。

### 15.3 开局战力指数（OPI）

OPI 只用于策划校准与验收，定义如下：

```text
OPI = 100 × (
  0.30 × 有效气血 / 基准气血 +
  0.25 × 十回合有效输出 / 基准输出 +
  0.20 × 有效承伤 / 基准承伤 +
  0.15 × 身法先手 / 基准身法 +
  0.10 × 功能覆盖 / 基准功能
)
```

其中：

- 有效气血 = 气血 + 护盾期望；
- 有效承伤 = 气血 /（1 - 综合减伤）；
- 功能覆盖 = 治疗、增益、控制、解控的覆盖率，按回合上限截断；
- 基准值取 T1 全角色平均，基准 OPI = 100；
- OPI 不落库、不进 contracts、不进道装领域，也不作为客户端展示的「战力」。

### 15.4 档位目标与验收带

| 档位 | 基准 OPI | 验收带 |
| --- | --- | --- |
| T1 | 100 | 95-105 |
| T2 | 120 | 114-126 |
| T3 | 145 | 138-152 |
| T4 | 175 | 166-184 |
| T5 | 210 | 199-221 |

设计意图：T5/T1 约 2.1 倍，不出现「一档碾压三档」；高献祭档的主要优势是稳定性、容错与成长速度，而不是开局数值爆炸。

### 15.6 为什么不做战力字段

- 道装领域已有明确约束：不得新增品质/战力字段，计算由属性与内容共同得出；
- 玩家侧显示「战力」会诱发跨系统比较，和现有境界/道装/功法展示重复；
- OPI 依赖模拟对局，不适合作为持久化真值。

对外展示建议：境界、灵根谱、本命道法、道装品阶、已学功法，不显示单一数字。

- 用现有 V6 投影拿到真实面板与技能列表；
- 在本地用现有战斗模拟跑十回合对局，记录有效输出、承伤、治疗/护盾覆盖；
- 按档位目标 OPI 调整随机道法预算与道装件数；
- 不新增常驻 benchmark/seed 脚本；临时评估脚本不入库。

## 16. 初始技能设计

### 16.1 三层结构

| 层 | 数量 | 性质 | 来源 |
| --- | --- | --- | --- |
| 本命道法 | 1 | 主动，角色固定 | 逐角色内容 |
| 随机道法 | 0-3 主动 + 1-3 被动 | 主动/被动混合 | 开局道法池 |
| 炼气功法 | 1 本已学 | 被动 | 现有 6 本炼气功法 |

设计目的：

- 本命道法保证角色识别，不是纯随机；
- 随机道法保证每局有差异；
- 炼气功法复用现有系统，不另造一套被动。

### 16.2 随机数量

| T3 | 1 | 1 | 1 | 1 本 | 2 |
| T4 | 1 | 2 | 2 | 1 本 | 2 |

- 被动道法总数不超过 4；
- 炼气功法层数不超过 3（现有炼气上限）；

| 档位 | 品阶 | 缩放 |

### 16.6 元素亲和权重

抽取时按角色首灵根加权：

| 关系 | 权重 |
| --- | --- |
| 本元素 | 3 |
| 生我元素 | 1.5 |
| 其他 | 1 |

五行相生：木生火、火生土、土生金、金生水、水生木。变异元素的「生我」按：冰←水、雷←火、风←木。

本命道法固定为本元素，因此「至少有一个本元素技能」由本命保证，随机池不再做强约束。

### 16.7 本命道法

- 每个角色 1 个，固定主动；
- 名字与效果转译自角色元素战技/爆发，但使用道友战斗原语；
- 本命道法不进入随机池，不能被重 roll；
- 本命道法可以随境界成长，但开局固定 1 级；
- 首批 36 个角色的本命见第 18 节表。

### 16.8 随机与落库

```text
templateId = `gi:${avatarId}`
seed = sha256(`${journeyId}:${templateId}`).readUInt32BE(0)

rngRoots  = deterministicRng(sha256(`${seed}:roots`))
rngSkills = deterministicRng(sha256(`${seed}:skills`))
rngGear   = deterministicRng(sha256(`${seed}:gear`))

本命 = template.signatureArtId
主动 = weightedSample(activePool, countActive, elementWeights, rngSkills)
被动 = weightedSample(passivePool, countPassive, elementWeights, rngSkills)
功法 = weightedSample(manualPool, 1, roleWeights, rngSkills)
```

- 灵根、技能、道装使用独立子种子（`:roots`、`:skills`、`:gear`），避免某一内容池变化导致其他部分漂移；
- 随机结果只在创建时生成一次；
- 结果写入 `wanjiedaoyou_cultivator_innate_arts`，存 artId、kind、source、quality、level、seed；
- 后续展示与战斗投影只读快照，不重新抽取；
- 内容池后续增删不影响既有角色。

### 16.9 与既有系统的关系

| 系统 | 关系 |
| --- | --- |
| 个人功法 | 开局只学 1 本炼气功法；额外功法以玉简入包，不占槽 |
| 宗门功法/神通 | 本命道法不替代宗门神通；两者可并存，按 ID 去重 |
| 道装器诀 | 器诀是主动技能来源之一；若随机到同名 ID，去重并顺延 |
| 器蕴 | 只提供被动/属性，不参与主动抽取 |
| 灵兽技能 | 开局不发放灵兽技能；灵兽后续单独捕捉/培养 |

### 16.10 战斗投影顺序

建议顺序：

```text
基础属性
→ 个人功法被动
→ 开局被动
→ 宗门被动
→ 道装器蕴/阵纹
→ 开局主动 + 本命
→ 宗门主动
→ 道装器诀
```

规则：

- 同名 ID 只生效一次，先到先得；
- 主动技能列表按「本命、开局主动、宗门主动、器诀」排序；
- 不改变现有行动规则、法力消耗、冷却与目标选择；
- 投影诊断新增 `OPENING_ART_UNKNOWN`、`OPENING_ART_REALM_LOCKED`、`OPENING_ART_DUPLICATE`。

### 16.11 降级实现

如果本期不批准新技能子系统，可用降级方案：

- 被动：随机 1-3 本炼气功法（但炼气只有 1 槽，多余只入包），实战被动仍只有 1 本；
- 主动：只靠开局道装的器诀（0-2 条）；
- 本命：暂时做成一本角色专属炼气功法（被动），不提供主动技能。

降级方案能上线，但无法满足「主动/被动随机」的完整体验，只作为风险兜底。

- 不发放可交易的稀有材料，避免开局经济套利。
- 灵石为档位总额，不再复用普通建号的 20,000 新手礼包。

### 17.5 发放方式

推荐用**一封「转世开局礼」邮件**承载全部物资，避免多封邮件与顺序问题：

- 标题：`转世开局礼`
- 正文：按档位生成一句叙述，说明献祭档位与所赠道装；
- 附件：灵石、丹药、灵果、玉简；
- 道装：在创建事务内直接生成实例并自动穿戴，不放入邮件（避免邮件领取时的随机性）；
- 若自动穿戴失败，则道装入包并记录诊断，不阻断建号。

### 17.6 幂等与审计

- `journey_id` 唯一；重复请求返回同一 `cultivatorId`，不重复发奖；
- 若首次事务失败，账本状态为失败/未完成，允许同 journeyId 重试；
- 记录：档位、种子、灵根、本命、随机技能 ID、道装实例 ID、邮件 ID；
- 管理端可查「某 journeyId 发了什么」，用于客诉与回滚。

### 17.7 绑定与流通

建议开局道装**绑定不可交易**。若现有 `inventory_items` 没有绑定字段：

- 方案 A：新增 `bound` / `source` 字段；
- 方案 B：在交易/拍卖/回收入口按 `source = 'opening'` 拦截；
- 方案 C：本期先不绑定，但限制器阶 10 的售价上限。

优先方案 B，避免为单一活动改表；若已有回收/交易过滤点，直接复用。

## 20. 验收标准

### 20.1 功能

- 5 个档位都能建号成功，且灵根数分别为 4/3/2/1/1；
- 每个角色的灵根谱都包含其原神元素首灵根；
- T5 道装为 6 件，全部器阶 10；
- 炼气初期（5 级）能穿戴全部开局道装；
- 开局只学 1 本炼气功法，额外玉简在包内；
- 开局道法主动不超过 3、被动不超过 4；含器诀的战斗主动总数不超过 6；
- 同一 `journeyId` 重复请求返回同一角色，不重复发奖。

### 20.2 随机与确定性

- 同一 `journeyId` 重建（清理测试数据后）得到相同灵根、技能、道装；
- 不同 `journeyId` 有可见差异；
- 内容池更新后，既有角色的技能快照不变。

### 20.3 安全

- 无内部密钥拒绝；
- `starterTier` 为 0、6、小数、字符串时拒绝；
- `avatarId` 越界拒绝；
- `combatPower` 不改变六维总和、技能数量、道装数量；
- 文本过滤命中时拒绝建号。

### 20.4 经济

- 开局礼只有一封，灵石为档位总额，不再叠加 20,000；
- 开局道装不可通过拍卖/交易/回收套利（按 17.7 方案）；
- T5 总物资价值有上限，不随 `combatPower` 增长。

### 20.5 战斗

- 本命、随机主动、器诀都能在战斗中出现且不重复；
- 被动合并后六维/减伤/暴击等数值在预算内；
- 不出现未解锁境界技能；
- 十回合模拟不出现无限循环、负治疗、护盾溢出。

pnpm run test

## 附录 B：随机伪代码

```ts
function buildOpeningBuild(input: {
  journeyId: string;
  template: CharacterTemplate;
  tier: 1 | 2 | 3 | 4 | 5;
}) {
  const counts = OPENING_COUNTS[input.tier];
  const seed = hashSeed(`${input.journeyId}:${input.template.id}`);

  const rngRoots = deterministicRng(hashSeed(`${seed}:roots`));
  const rngSkills = deterministicRng(hashSeed(`${seed}:skills`));
  const rngGear = deterministicRng(hashSeed(`${seed}:gear`));

  const roots = buildRoots(
    input.template.rootLine,
    counts.rootCount,
    rngRoots,
  );

  const active = weightedSample(
    ACTIVE_POOL,
    counts.active,
    elementWeights(input.template.element),
    rngSkills,
  );
  const passive = weightedSample(
    PASSIVE_POOL,
    counts.passive,
    elementWeights(input.template.element),
    rngSkills,
  );
  const manual = pickManual(input.template, rngSkills);

  return {
    roots,
    signatureArtId: input.template.signatureArtId,
    active,
    passive,
    manual,
    equipment: buildStarterEquipment(input.tier, input.template, rngGear),
    supplies: STARTER_SUPPLIES[input.tier],
  };
}
```
